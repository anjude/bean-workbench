# 工作台规范

## 目标

工作台用于沉淀个人 Agent 能力，包括 `skill`、知识库、任务索引和常用脚本，并承担业务仓之间的全局路由、上下文聚合和跨仓编排职责。

## 核心闭环

1. 用户提出需求。
2. 工作台根据热任务、知识库和路由 skill 定位业务仓、协议仓与上下文。
3. Agent 在对应业务仓完成代码或文档产出；跨仓影响由工作台编排。
4. 需求结束后复盘可复用经验、反复问题和上下文缺口。
5. 将稳定经验沉淀回 `skill`、`knowledge-base/` 或 `script/`。

## 目录职责

- `.agents`：跨项目复用的 skill 实体目录，随工作台一起提交；模板和流程清单放各 skill 的 `references/`。
- `docs/`：工作台说明类文档，平铺不分层。
- `knowledge-base/`：可复用知识库，按公共知识、业务仓和系统分层。
- `task/`：工作台任务记录、热任务索引和痛点记录。
- `script/`：工作台辅助脚本。
- `business-repo/`：业务仓集合，包含后端、前端、协议等独立仓，不承载工作台规则。

## 演进原则

1. 新能力先进入任务记录或知识库。
2. 复现稳定后再升级为 skill。
3. 机械重复操作再升级为脚本。
4. 根目录保持克制，新增长文档优先放入 `docs/`。
5. 模板、清单、工作流这类执行期材料跟着对应 skill 走，不放进 `docs/`。

## Skill 目录规则

`.agents/skills/` 是统一的 skill 入口，不应长期把可复用 skill 散落在业务仓私有目录中。

skill 留在工作台仓库里，是为了跟着工作台一起做版本管理：提交、回滚、查历史都只有一处。跨项目共享靠外链解决——`~/.agents` 指向工作台的 `.agents`，其他 Agent 工具读 home 目录下的 `.agents` 就能拿到同一套 skill；某个项目想在仓内也看到，再建 `ln -s ~/.agents <项目根>/.agents`。

代价是改动全局生效，因此：

- 改 skill 前确认这次改动是否应当影响所有接入的项目。
- 只想在工作台内试的改动，用 `git stash push -- .agents` 隔开。

### 命名格式

统一使用：

```text
{族群前缀}-{阶段号}{阶段内序号}-{能力后缀}    阶段 skill
{族群前缀}-tools-{能力后缀}                  工具 skill，不占阶段号
```

示例：

- `dev-flow-0000-plan-flow`：dev-flow 族，00 方案设计阶段入口
- `dev-flow-0103-api-flow`：dev-flow 族，01 后端开发阶段第 3 项
- `dev-flow-0202-data-flow`：dev-flow 族，02 前端开发阶段第 2 项
- `dev-flow-0301-verify-flow`：dev-flow 族，03 整体验证阶段第 1 项
- `dev-flow-tools-repo`：dev-flow 族工具 skill，不占阶段号
- `bn-0101-creation-flow`：bn 族，01 创作阶段第 1 项
- `wb-0001-router`：wb 族，00 入口阶段第 1 项

### 命名原则

1. 目录名使用小写英文和连字符。
2. 族群前缀：`dev-flow` 跨端开发、`bn` 内容生产、`wb` 工作台基建。开发流水线不分前后端族群，两端各占一个阶段位。
3. 编号占四位，前两位是阶段号，后两位是阶段内序号；`xx00` 留给该阶段的总控或入口，具体 skill 从 `xx01` 起顺排。
4. `dev-flow` 族阶段语义：`00` 方案设计、`01` 后端开发、`02` 前端开发、`03` 整体验证；纯前端需求跳过 `01`，纯后端需求跳过 `02`。`bn` 为 `00` 素材、`01` 创作、`02` 复盘；`wb` 为 `00` 入口、`01` 路由与维护。
5. 横切能力建工具 skill，命名 `{族群前缀}-tools-{能力后缀}`，供所有阶段调用，不占阶段号。
6. 后缀表达动作或职责，如 `plan-flow`、`api-flow`、`verify-flow`、`knowledge-base`。
7. 目录名、`SKILL.md` 的 `name` 字段、文档引用三者必须一致；完整编号表见 `AGENTS.md`。
8. 一个阶段内的 skill 按「总是一起走」的粒度合并，不按技术动作切碎；合并后重排阶段内序号。
9. 避免使用 `.workbuddy`、平台名、产品壳名或纯个人偏好的目录命名，除非该目录确实是兼容层。

### 迁移原则

1. 业务仓里出现稳定复用的 skill 时，应优先迁移到 `.agents/skills/`。
2. 迁移时同步更新触发词、引用路径、任务记录和知识库入口。
3. 对历史 skill 保持兼容，但新增 skill 不再引入品牌化目录命名。

## 变更边界

1. 工作台建设默认只改根级工作台目录；skill 就在这批目录里，改动会经 `~/.agents` 外链同步给所有接入方。
2. 除非是明确业务需求，不直接改动 `business-repo/` 下的业务仓内容。
3. 工作台文档不复制业务仓的大段实现细节，只记录路由、约束、知识索引和可复用经验。
4. 第三方原始文档、许可证和临时导入代码默认保持原样。
5. 新增业务子仓时，工作台层必须联动检查 `business-repo/` 索引、`task/registry.md`、`knowledge-base/`、相关 `skill` 及其 `references/`，确保路由、职责和沉淀入口一致。
6. 新建任务目录前，必须先检查最近几个任务目录；若属于同类、零碎补充或同一上下文链条，优先合并到现有任务继续记录。

## 文档原则

1. 工作台 `md` 文档统一使用中文。
2. 专业术语、业务术语、代码标识、接口路径可以保留英文。
3. 根目录保持轻量，详细规范放入 `docs/`。
4. 避免重复内容：入口文档只做导航，细节放到专门文档。
5. `docs/` 只放说明类文档，平铺不分目录；模板和工作流下沉到对应 skill 的 `references/`，知识内容进 `knowledge-base/`。
