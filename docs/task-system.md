# 任务管理规范

## 目标

`task/` 用于记录工作台建设任务、热任务、冷任务和上下文范围，帮助 Agent 快速理解最近在做什么。

## 文件职责

- `task/registry.md`：热任务、冷任务、任务目录和资源范围索引。
- `task/pain-points.md`：痛点记录，按待处理和已处理分组。
- `task/YYMMDD_slug/`：单个工作台任务目录，例如 `260614_workbench-init/`。
- `task/YYMMDD_slug/README.md`：任务说明、边界、状态和沉淀记录入口。

任务 README 与复盘模板见 `.agents/skills/wb-router/references/`（`task-readme.md`、`task-review.md`）。

## 边界

工作台任务只记录工作台层面的目标、规则、沉淀和路由信息。业务仓具体实现、接口变更、测试细节应记录在业务仓自己的文档或提交中。开发需求的方案文档同样落在 `task/YYMMDD_{主题}/README.md`，模板见 `dev-flow-0000-plan-flow`。

## 任务命名

使用 `YYMMDD_slug/` 目录格式。`slug` 使用短英文或拼音，保持可搜索。

## 任务目录建议

- `README.md`：任务目标、范围、边界、状态。
- `handoff/`：会话交接，每份是当前状态快照，按时间戳命名，最后一份最新。高层，一屏读完就知道下一步干什么。
- `process/`：阶段过程记录，一个阶段一份 `{阶段号}-{环节名}.md`。记该阶段做了什么、得出什么结论、哪些判断被推翻了。细节全留这边。
- `review.md`：任务完成后的复盘和可沉淀内容，按需创建。

`handoff/` 与 `process/` 的分工：**handoff 是「我从哪接着干」，process 是「这件事是怎么被想清楚的」**。handoff 里指向 process 文件，不复制过程内容。写法见 `wb-handoff`。

`process/` 在任务目录和 beannote 选题目录里都存在（`business-repo/beannote/topics/{topic}/process/`），命名写法一致，差别只在阶段号跟着谁的流水线。选题那边的骨架由 `bn-0000-init-flow` 建。

## 热任务规则

热任务用于加速路由到最近上下文。任务完成或长期不活跃后，应从热任务移到冷任务。

## 新任务合并规则

新增任务目录前，先看最近几个任务目录和 `task/registry.md`：

1. 如果新任务和最近任务属于同一业务线、同一流程或同一问题链，优先合并到已有任务目录继续记录。
2. 如果新任务只是原任务的补充、修补、验证或零碎收口，也优先继续共用原任务上下文。
3. 只有当任务目标、边界或沉淀对象明显不同，才新建任务目录。
4. 合并后要在任务目录 README 里说明这是延续任务，避免后续再拆分。

## 子仓接入任务

当工作台接入新的业务子仓时，应创建或更新一个对应任务目录，记录：

1. 子仓名称与仓位
2. 需要同步的 `skill`
3. 需要更新的知识库和路由提示
4. 是否需要新增工作流或检查脚本
5. 验证结果和遗留风险

这类任务用于保证“加子仓”不是只改 `.gitmodules`，而是完成工作台级整体收口。

## 提交流程

工作台根目录应提供统一的 `make commit` 命令，用于提交当前工作台全部变更。文档和任务记录中提到“提交工作台内容”时，默认指向该命令，而不是在对话里手工拼命令。提交信息直接取 `make commit` 后面的参数，多个参数用空格拼接；不带参数时使用默认提交信息。
