# 收敛（03 阶段）

## 这一步解决什么

改稿最容易犯的错是不分层乱改——用户说"这段不对"，可能是事实错、可能是点选错、可能只是讲法别扭。改错层，越改越糟。

| | |
|---|---|
| 用户在这一步说什么 | "这段不行"、"太 AI 了"、"逻辑不通"、"换个角度" |
| agent 做什么 | 归层 → 按层改 → 每轮只改一个量级 → 报改了什么 |
| 产物 | 对话里的新版全文（默认）；用户说写入才落盘 |
| 停下等什么 | 用户说"可以了"或指出下一处 |

## 反馈归层

| 反馈指向 | 属于哪层 | 回哪一步 |
|---|---|---|
| 观点不对、事实错、这件事不是这样 | 思考 | `bn-0000-think-flow` |
| 讲偏了、该说的没说、不该说的说了一堆 | 梳理 | `bn-0100-shape-flow` |
| 太 AI、像提纲、读不下去、这段别扭 | 表达 | `bn-0200-express-flow` |

拿不准归哪层，先问一句再改，别猜着改。归错的代价是改完还是不对，还多花一轮。

## 改稿规矩

- **每轮只收敛一个量级的问题**：先解决"这段要不要存在"，再解决"这段怎么讲"，最后才是措辞。一次改十处，用户得重看全文。
- **默认不落盘**：改稿先在对话里给完整全文，用户明确说「写入 / 保存 / 落库 / 改上去」才动文件。唯一例外是某篇的首次生成，那属于交付。
- **正文只有两种形态**：对话里贴完整全文，或全文落库。不存在只给改动片段、只给 diff、用"其余不变"代替原文。用户读不到全貌就判断不了整体协不协调。"相对上一版的变化"放在全文之后做附注。
- **不辩解**：用户说某段不行，先改；改完再判断是不是规则盲区。

## 规则沉淀

改完判断这次是"当前稿的一次性问题"还是"可复用规则缺口"：

- 同类问题在不同稿件里重复出现 → 规则缺口，去改 skill 或 references
- 用户明确指出某种写法不要再出现 → 进 `references/表达红线.md`
- 只是本篇的事实修正、标题取舍、局部措辞偏好 → 不升级成规则
