# 选题与大纲（00 阶段，选题 + 讨论合一）

## 这一步在做什么

| | |
|---|---|
| 用户在这一步说什么 | "想写 XX"、"这个热点能不能写"、"这个题怎么切" |
| agent 做什么 | 读 playbook、查素材、反问 1-3 个关键问题、选题排雷、定平台；再做主题分析、模式判断、出总体大纲（选题判断 + 核心内容摘要七字段 + 写法方向）、走偏自查、拿到确认。**全程默认不落盘** |
| 产物 | 对话中的总体大纲（默认）；`topics/{日期}_{主题}/`（含 `01_大纲.md` + `manifest.yaml`）+ 重跑 `topics/索引.md`（**仅用户明确要求写入时**） |
| 停下等什么 | 用户说"大纲 ok"（落笔闸门，未确认不得成稿） |

上游交接物：用户的一句话灵感或热点
下游指向：`bn-0101-draft-flow`

通用交互规则（一次最多问 3 个问题、每步结束必须停、先给判断再解释、不辩解）见 `bn-tools-content-context`。

---

选题和讨论不再分两张卡。本阶段一次产出「总体大纲」：先把选题立住（写给谁、结论、核心问题、标题草案、排雷），再在同一份文档里把讨论结论压实（定位、最狠结论、反差、骨架含写法方向、锚点、边界、核实）。用户确认这份大纲后才允许成稿。

## 接需求后先做

1. 读取 `business-repo/beannote/docs/content-playbook.md`（项目级定位优先级高于本 skill 旧规则）。
2. 判断平台：用户说公众号→公众号文章；说小红书→图文；未说→中性，两边可改。
3. 查素材：命中书籍 / 演讲 / 访谈 / 股东信等长期素材，用 `bn-tools-knowledge-base` 整理进 `knowledge-base/`；已有条目直接读。
4. 先给判断再展开：用户抛想法，先说"这题能写 / 不能写，理由"，再反问（一次 ≤3 个）；问完要有自己的判断，不发问卷。

## 选题排雷

选题阶段必须查是否烂大街模板：

- 读者看标题就能猜出全文结构与结论（"到了年纪要注意这些坑"）。
- 同一结构在财商号反复用，换数字换马甲。
- 核心逻辑是"到某节点→这些坑→这样处理"。

命中任一条，直接告诉用户这题老化，建议放弃或找反常识切口；别靠文风救选题本身。

## 讨论第一步：主题分析（先确认想表达什么，不谈写法）

讨论环节禁止一上来给写法建议（结构、手法、"用 X 砸 Y"、案例怎么排、要不要加反转）。先做主题分析，把「这篇到底想表达什么」立住，写法放到最后一层。

顺序固定三步：

1. **拆题**：这个主题由哪几层构成，分别是什么（定义层 / 机制层 / 条件层…）。先拆开、别急着站队——参照 `references/认知深度方法论.md` 方法一「先拆后判」。
2. **列跑偏**：这题最容易写歪成什么（语录汇编 / 只讲定义的概念科普 / 过度否定变成劝短线 / 荐标的…）。认出跑偏项才知道要避什么。
3. **立主判断**：一句话说清这篇想让读者看到什么。是「看到」，不是「改变他的看法」——不要求每篇都承担说服或教学任务，把内容摆清楚、让人有收获感即可。这句没立住，不许往下走，更不许谈写法。
4. **理脉络**：把主判断拆成一条读者能走下来的推导链（详见下一节）。**主判断是终点，脉络是路**——只有终点没有路，读者看到的是一句断言；有了路，他才会觉得这件事是有内在逻辑的。

主判断与脉络都被用户确认后，才进入写法层：骨架（含写法方向）、锚点、结构、标题。**骨架的写法方向服务于主判断，禁止由写法倒推主题。**

走偏信号（命中任一项回到主题分析）：讨论开场就谈「怎么写更有冲击力」「用什么案例砸」；或主判断还没定就开始排骨架顺序、挑标题。

## 脉络（推导链）：主判断凭什么被接受

**骨架写"每节讲什么"，脉络写"读者怎么被带过去"。** 骨架对了，文章仍然可能是几块并列内容；脉络对了，读者才会被一步步带到结论，并且觉得自己是走过去的、不是被塞的。

每步一行，写三件事：读者此刻在哪 → 这一步抛出或解决什么疑问 → 推出什么交棒给下一步。6-8 步为宜，一步约等于骨架一节。

硬要求：

- **单向推进**：每步只能从上一步的答案里长出来（因果 / 递进 / 检验 / 换个尺度问）。并列堆砌不是脉络。
- **禁序号式衔接**：出现"还有一个问题""最后一个""再看一个"，说明两步之间没推导关系，补桥或删步。
- **写读者状态，不写素材清单**：每步是"读者此刻手里有什么 / 已经看到什么"，不是"介绍 X 概念""讲 Y 案例"。
- **现象不写成"读者以为"**：起点是现象就陈述现象（"多数人进场时的打算是捞一笔就走"），别写成"读者以为自己会捞一笔就走"——后者把事实降级成认知偏差，还替读者下定义。读者此刻在哪，指的是他手里的信息和已发生的事，不是他哪里想错了。
- **不许跳步**：读者还没接受 A，就跳到 A 推出来的 B，等于自己跟自己对话。

自检三条（写完必做，写在模板里）：抽掉任一步后一步是否悬空；只读脉络能不能推出主判断；有没有哪步在换个说法重复上一步。

**跟骨架的关系**：先定脉络再定骨架，骨架是脉络的落地（每步对应一节 + 写法方向）。脉络改了骨架必须跟着改。审议顺序也是先脉络后骨架——脉络接不上就改顺序蒙混，等于把洞藏起来。

## 主题层与角度层分离

主题和角度不是一回事，讨论时先分清，避免改一次角度就把主题换掉：

- **主题层（不动）**：这篇要回答的那个问题本身，如「价值投资和长期投资的关系」。
- **角度层（可换）**：切入方式、标题、开场钩子、引流切口。同一个主题可以换多个角度，换的是进门方式，不是要回答的问题。
- **判定规则**：某一节写着写着跟主题没了关系，删该节，不是改主题。角度是服务主题的，不是主题本身。
- **落到大纲**：骨架里标清哪几节属角度层（引流 + 立机制）、哪几节属主题层；角度层写完必须交回主题层，不能自成一统。换角度时只动开场与标题，主题层落点不变。

用户指方向、给角度、换标题时，先确认它落在哪一层：只换角度就别动主题与主题层骨架；要改主题才重做主题分析。

## 落盘规则（内容默认不写，结构可保留）

分两层，别混：

| 层 | 包含 | 规则 |
|---|---|---|
| **结构层** | `topics/{日期}_{主题}/` 目录、`manifest.yaml` 及其结构性字段（`topic` / `status` / `platform` / `form` / `created` / `slots`） | 开题时建立，之后一直保留，不算「落库」 |
| **内容层** | `01_大纲.md` 的正文内容；manifest 的 `conclusion` / `mode` / `next` / `decisions`；往 `knowledge-base/` 追加本篇内容 | **默认不写**，只有用户明确要求才动 |

`topics/索引.md` 由 manifest 派生，任何一层变更都随之重跑，它本身不是独立的落库动作。

**讨论阶段的内容默认只停留在对话里**：主题分析、主判断、骨架、写法方向、标题草案、事实源清单——一律先讲给用户听，不当作已定稿写进文件。

只有用户**明确要求**落库时才写内容层（措辞如"写入""落库""存下来""写进大纲"）。未拿到指令前，讨论产出视为**可随时推翻的草稿，不留痕**——这正是讨论阶段该有的状态：改主意不需要回滚文件。

用户要求写入内容时，按下一节一次性落地，不要分步零星写。

## 开题动作

顺序落地（目录与槽位规范见 `bn-tools-content-context`）：

1. 归档检查：`topics/` 根有不属于当前月的目录，先按 `YYYY-MM/` 搬走并改索引。
2. 建目录：当前月建 `topics/{日期}_{主题}/`；往月直接建 `topics/{YYYY-MM}/{日期}_{主题}/`。
3. 建 `manifest.yaml`（模板见 `bn-tools-content-context/references/manifest模板.yaml`），**此步只填结构字段**：`topic` / `status=在制` / `platform` / `form` / `created` / `slots`；`mode` / `conclusion` / `next` / `decisions` 留 `null` / `[]` 占位，等用户要求写内容时再填。
4. 重跑索引：`topics/索引.md` 由 manifest 派生，不手改。

**结构层到此为止。** 下面两步属于内容层，只有用户明确要求"写入 / 落库 / 存下来"才执行：

5. 写 `01_大纲.md`，模板见 `references/大纲模板.md`。
6. 补 manifest 的内容字段：`mode`（强判断默认）/ `next=大纲待确认` / `conclusion` 态度版 / `decisions`（含被否切口），然后重跑索引。

先建目录再写大纲。

## 总体大纲怎么写

一份文档，分三段：

**第零段｜主题分析**（拆题 / 跑偏 / 主判断 / **脉络**，模板见 `references/大纲模板.md`；主题分析未确认前不许展开写法）

**第一段｜选题判断**（立住选题）

- 写给谁（一句话，别写"所有人"）
- 一句话结论（中性；态度版最狠句留到第二段结论）
- 核心问题（1-3 个）
- 标题草案（3 个 + 备选）

**第二段｜核心内容摘要（生产闸门）**

严格按七字段、顺序固定：定位 → 结论 → 反差 → 骨架 → 锚点 → 边界 → 核实。

- **骨架**字段每节一行，但每节须同时带「写法方向」（用哪个例子、什么手法、避什么坑）——把原选题卡的「主题概览」并进来，定调不写正文。
- 强判断模式：结论须最狠、有态度。
- 事实流模式：结论改「事实陈述 / 核心机制」；「结论含糊没态度」「骨架只是资料罗列」降级为可选，其余走偏信号仍生效；须保留免责声明，不得替读者下买卖 / 对错结论。

模式默认强判断；用户明确要求"少判断、给事实、让时间证明"时转事实流。定下写进 `manifest.yaml` 的 `mode`。

### 走偏信号（命中任一项先改大纲再确认）

- 强判断专属：结论含糊、和稀泥、没态度（"值得关注""未来可期"）
- 反差缺失或落入俗套（"到了年纪要注意这些坑"三段式）
- 强判断专属：骨架只是资料罗列、没有判断维度
- 边界写不清（点名具体公司做批判、或没提免责声明）

## 确认门

大纲写完后必须显式向用户确认（"大纲 ok 吗？"）。拿到明确确认后才允许成稿；禁止跳过确认直接写正文。用户修改任意项，先改大纲对齐再写正文。

拿到"大纲 ok"后分两种状态：

- **已落盘**（此前用户明确要求写入过）：把态度版最狠结论写回 `manifest.yaml` 的 `conclusion`，`mode` 确认写入，追加 `decisions`（含被否切口），`next` 改「成稿」，重跑索引。
- **未落盘**：保持对话态，不写任何文件。"大纲 ok"只表示进入成稿阶段，不等于自动建库；要不要存由用户再说。

已确认大纲进入生产后作为「选题判断」区骨架直接复用，不另起炉灶。

## 正文策略（写稿前在脑中过一遍，详见 `bn-0101-draft-flow`）

主判断、氛围、入口、增量信息、支撑物、合规边界、结尾方式。去平庸标准：只剩空话 / 标题拿掉能套任何题 / 每段只在解释上一段——必须重写。
