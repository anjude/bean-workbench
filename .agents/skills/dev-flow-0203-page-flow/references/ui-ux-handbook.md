# 通用 UI/UX 模式手册

## 目的与边界

本手册为跨项目、跨平台的业务界面提供可复用的交互决策规则，重点覆盖列表、详情、编辑、操作菜单、删除和排序等常见模式。它规定如何选择和组合模式，不规定所有产品必须长成同一种视觉样式。

本手册是设计起点，不代替需求规格、用户研究、无障碍要求或目标平台的交互规范。遇到冲突时，按以下顺序处理：明确的产品需求与领域语义、目标平台的可用性要求、项目既有设计系统、本手册的通用建议。记录需要长期复用的新决策，避免同一模式在不同页面上悄悄分叉。

后端协议及枚举使用唯一协议事实来源；运行时平台能力由客户端适配层封装。页面层只表达产品需要的 UI、UX 和交互差异。

## 决策顺序

设计一个页面或操作时，依次明确：

1. **对象和任务**：用户正在看什么对象，来这里要完成什么。
2. **主要动作**：当前页面最重要的一项动作是什么；其他动作按频率、风险和上下文排序。
3. **对象状态**：动作在当前状态是否可用，执行后状态如何改变。
4. **风险与可恢复性**：是否会丢数据、影响关联对象、难以撤销或产生外部副作用。
5. **页面关系**：列表、详情、编辑之间如何进入、保存、取消和返回。
6. **输入与平台**：触控、鼠标、键盘、屏幕尺寸和系统能力是否改变入口形式；不因此改变领域语义。

不要先从“按钮放哪里”开始。先确定对象、动作和状态，再选择页面结构与控件。

## 视觉一致性与控件反馈

- 重复使用的颜色、文字层级、间距、圆角、边框和层次效果优先来自项目语义令牌。令牌表达用途（如页面背景、次级文字、危险操作），不把某个主题的具体颜色名暴露给页面。
- 只有被多个页面或组件复用、且含义稳定的值才提升为共享令牌；一次性布局值可留在局部样式，避免令牌膨胀。
- 同一产品内，同类控件的图标风格、尺寸层级和交互反馈保持一致。优先复用项目已有图标来源；不要为单个页面引入另一整套图标系统。
- 图标单独承担动作时，应有清楚、可访问的名称；不常见或可能歧义的动作配文字说明。
- 可点击控件需有可感知的按下、禁用和忙碌状态。禁用不应只靠颜色表达；异步操作期间防止重复触发。
- 点击区域彼此重叠或嵌套时，明确哪个区域负责打开对象、哪个负责行内动作，避免一次点击同时触发两个结果。

## 页面模式

### 页面初始化与内容加载

- 区分应用启动所需的全局前置数据、当前页面数据和局部区域数据；只阻塞依赖尚未就绪数据的内容，能独立展示的页面框架可保留。
- 首次加载且没有可用内容时使用清楚的加载反馈；刷新或重新请求已有内容时，优先保留当前内容并显示局部进度，避免整页闪空。
- 初始化失败和页面请求失败要区分处理。失败界面说明当前内容为何不可用，并提供合理的重试、返回或重新进入路径。
- 数据仍在加载时，不把暂时的零条数据误呈现为“空列表”，也不要提前显示创建引导。

### 列表页

列表帮助用户浏览、扫描、比较和定位一组对象。

- 每行先呈现最有助于识别对象的主信息；次要信息支持判断，不与主信息争夺视觉焦点。
- 同类行保持一致的信息顺序、点击范围和操作反馈。
- 整行可进入详情时，给出一致且可感知的导航 affordance；行内另有按钮时，明确区分“打开对象”和“执行动作”的点击区域。
- 高频且关键的创建或筛选操作应容易发现。低频、对象相关的操作可收纳到行菜单或上下文入口。
- 排序、筛选、分组和置顶是不同的组织方式，呈现时要让用户能理解当前列表为何这样排列。
- 定义首次加载、刷新、分页加载、无结果、空集合、失败和重试状态。空集合可以引导创建；筛选无结果应提供清除或调整筛选的路径。

### 详情页

详情页帮助用户理解单个对象，并完成与该对象相关的主要后续任务。

- 页面开头清楚标识对象及其关键状态，用户从列表跳转后能确认自己打开了哪个对象。
- 按用户决策顺序组织内容；将状态、重要属性、正文和次要元数据区分层级。
- 页面主要动作应与对象当前状态相符。编辑等常用动作应容易找到；删除等高风险动作采用明确、稳定的入口。
- 有关联记录、子对象或历史记录时，说明关系和动作影响范围，不让用户误以为只作用于当前显示的一条内容。
- 定义对象不存在、无权限、加载失败、内容为空和操作失败时的回退路径。

### 编辑页或编辑态

编辑界面帮助用户安全、可预期地修改对象。

- 字段标签、格式、约束和默认值应与用户理解的业务概念一致；必填和校验规则在提交前可发现。
- 输入错误尽可能在相关字段附近解释，并保留用户已输入的内容。
- 保存期间给出进行中反馈，防止重复提交；成功后明确说明结果，并按任务目标返回详情、列表或保持在编辑上下文。
- 取消、返回或切换对象可能丢失未保存内容时，依据数据价值和恢复能力决定是否提示；避免对不会丢失内容的操作添加多余确认。
- 新建和编辑可共用表单结构，但标题、主按钮、初始值、成功后的去向和错误处理应符合各自任务。

## 操作与菜单

### 动作层级

- 一屏或一个对象上下文应有清楚的主要动作；次要动作保持可找到，但不与主要动作争夺注意力。
- 高频或完成当前任务必需的动作，不应只藏在难以发现的手势或菜单里。
- “更多”适合收纳低频、次要、与当前对象相关的动作。菜单项使用简短、明确的动作词，并按常用程度和逻辑关系排序。
- 菜单保持精简。动作过多时重新检查功能分组、页面信息架构或是否应进入独立管理流程，不要无限加长菜单。
- 同一动作在列表、详情和其他上下文中出现时，名称、图标含义和结果保持一致；入口可按平台习惯变化。

### 编辑

- 编辑入口应靠近其作用对象或对象的主要操作区。
- 若编辑是完成任务的核心步骤，应使用可见入口；若只在特定选择或管理模式中出现，说明进入该模式的方式。
- 保存、取消和离开编辑态的结果应明确，尤其是未保存内容的处理。

### 删除和其他高风险动作

- 先判断动作是否可撤销、影响多少对象，以及是否会触发级联或外部副作用；按实际风险决定即时撤销、确认、二次验证或权限控制，不把确认弹窗机械地加到每个删除操作。
- 确认信息应指出将作用于哪个对象，以及重要的连带影响；确认按钮使用明确动作词，避免模糊的“确定”。
- 将危险动作与主要的保存、完成或导航动作在视觉和位置上区分开。
- 删除执行中防止重复触发；成功后从当前上下文中移除对象并给出反馈。若支持撤销，清楚说明撤销时限或结果。
- 删除失败时保留上下文和必要输入，解释失败并提供可行的重试或恢复路径。

## 置顶、移至最前与排序

先区分**状态**和**动作**：置顶可以是条目的持久状态，移至最前是改变当前排序位置的动作。名称应描述用户执行后会发生什么，而不是只复述字段或实现方式。

- 如果置顶状态通过时间戳排序，且再次置顶会更新该时间戳，那么已置顶条目再次操作的实际结果是“移至最前”，不是再次改变置顶状态。可按状态提供准确动作名：未置顶条目显示“置顶”；已置顶但未排第一的条目显示“移至最前”；已经排第一时隐藏该动作或显示“已在最前”。取消置顶应作为独立且明确的动作。
- 如果产品中的置顶只表示持久状态，不改变同组条目的相对顺序，就保留“置顶/取消置顶”这组状态动作，不用“移至最前”代替。
- 如果“移至最前”只改变一次性排序、不产生置顶状态，则需要明确反馈它不会形成持久置顶。只有两者语义相同时才合并动作；语义不同时要让用户看懂区别。
- **排序**表达集合的排列规则，例如按时间、名称或状态排列；切换排序不应悄悄改变对象本身的属性。
- 操作成功后及时更新列表顺序，并提供足够反馈让用户确认变更。明确相同排序值下的稳定次序，避免刷新后对象无故跳动。
- 拖动排序、菜单命令和快捷按钮可以因输入方式不同而不同，但最终的顺序语义与保存结果一致。

## 浅色、深色与跟随系统

浅色、深色和跟随系统是产品的标准主题模式。主题既影响视觉呈现，也影响可读性、状态辨识和用户对系统偏好的控制；新页面与组件应完整适配三种模式。

- **浅色**和**深色**是用户明确选择的固定外观。切换后立即应用到全局界面，并在产品定义的偏好范围内持久生效。
- **跟随系统**表示读取操作系统当前外观；系统外观变化时，应用自动切换，不覆盖用户的模式选择。
- 首次使用时的默认模式和偏好保存范围由产品统一定义。用户选了浅色或深色后，不应因系统外观变化而被悄悄改回跟随系统。
- 颜色使用语义化主题令牌，例如页面背景、表面、主文字、次级文字、边框、强调色和危险色；组件与页面消费令牌，不在局部硬编码一套仅适用于单主题的颜色。
- 两种外观下保持相同的信息层级、交互语义和状态含义。颜色不能成为区分成功、警告、错误、选中或禁用状态的唯一线索。
- 首屏渲染应尽量避免先显示错误主题再闪切；主题切换应覆盖页面、弹层、菜单、空状态、图表、图片占位和系统栏等可见表面。
- 平台提供原生主题能力时按平台规则接入；能力不一致时由主题/平台适配层统一处理，业务组件仍使用相同主题语义。
- 验收时分别检查浅色、深色、跟随系统，以及系统主题运行中切换；覆盖主要页面状态和文本/图标对比度。

## 反馈与异常状态

每个会改变数据或页面状态的动作都应定义完整反馈：

| 阶段 | 设计要点 |
| --- | --- |
| 可操作 | 当前对象状态、权限和可用动作清楚 |
| 进行中 | 明确正在执行；避免重复提交或互相冲突的操作 |
| 成功 | 展示结果变化；必要时提供撤销、继续或返回路径 |
| 失败 | 保留上下文，说明问题并提供恢复办法 |
| 空或无结果 | 区分尚无对象、筛选无结果、对象内容为空 |
| 不可用 | 对关键功能说明原因或恢复条件，不制造无响应的控件 |

反馈方式由动作重要性、持续时间和是否需要用户决策决定。短暂、可恢复的结果可用轻量反馈；需要用户作出选择或理解风险时才使用阻断式对话。

## 弹层与固定操作区

- 弹层或底部面板适合短暂、聚焦且与当前上下文相关的任务；内容过多、需要复杂浏览或长期编辑时，应考虑独立页面。
- 需要确认或选择时，明确标题、对象、后果和可选动作；提供符合风险的取消或关闭路径。点遮罩是否关闭应与误触后果相匹配。
- 固定在屏幕边缘的主要操作区只用于持续可达确有价值的动作。避免遮住滚动内容、输入法或系统控件。
- 移动端底部操作区和面板需处理系统安全区；内容区预留相应空间，确保最后一项内容和主按钮都能完整触达。
- 软键盘出现时，编辑字段、校验信息和提交操作应仍可见或可通过滚动到达；键盘收起后布局恢复稳定。

## 跨平台表达

- 保持业务对象、动作语义、数据结果和失败处理一致。
- 触控端、桌面端和小程序可以使用不同的入口形式，例如可见按钮、溢出菜单或上下文菜单；不得让关键操作只依赖长按、悬停或其他不可见手势。
- 平台原生控件、焦点顺序、键盘操作、读屏标签、点击目标和系统导航按目标平台规范处理。
- 平台 API、存储和运行时兼容问题归适配层；页面层只为真实的产品体验差异保留平台分支。
- 小屏和大屏可调整信息布局与导航结构，但保持主次层级和任务路径清晰。
- 固定按钮、弹层、输入法和安全区的具体实现可按平台调整，但不能遮挡内容或造成操作无法完成。

## 模式记录模板

新增或调整一条长期模式时，按下面结构记录决策，避免把场景假设写成无条件规则：

```markdown
### 模式名称

- 目的：解决用户的什么任务。
- 适用条件：哪些对象、状态和场景使用。
- 决策规则：如何选择入口、动作优先级和交互方式。
- 状态与反馈：进行中、成功、失败、空和不可用时如何表现。
- 跨平台表达：哪些是稳定语义，哪些允许按平台调整。
- 例外与依据：例外场景、产品决策或平台规范来源。
```

更新时保留仍有效的原则，删除过时或互相矛盾的规则；附上来源链接或对应项目决策。遇到平台建议不一致时，记录差异和采用理由，不把某个平台的行为误称为行业统一标准。

## 交付前检查

- 用户能否看懂当前对象、主要动作和操作结果？
- 列表、详情、编辑之间的进入、保存、取消和返回是否连贯？
- 菜单里的动作是否与当前对象相关、命名明确且数量可控？
- 高风险动作是否按实际影响处理，并解释删除或变更范围？
- 置顶、排序和手动重排的语义是否一致且可预测？
- 置顶作为状态和移至最前作为动作是否区分清楚？已有置顶条目再次操作时，文案是否描述真实结果？
- 浅色、深色和跟随系统是否都能正确应用、持久化并覆盖页面状态？
- 首次加载、后台刷新、空列表、无筛选结果、失败和重试是否区分？
- 图标、样式令牌、按下/禁用/忙碌反馈是否与同类页面一致？
- 固定操作区、面板、软键盘和系统安全区是否互相避让？
- 权限不足、重复提交和恢复路径是否考虑？
- 是否把平台运行差异留在适配边界，同时保持各端交互入口可发现、可访问？
