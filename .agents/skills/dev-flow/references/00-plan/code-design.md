# 代码方案与实现原则

涉及代码改动时，阶段 02 用本文选择实现方案，阶段 03 用本文检查实现和评审 diff。前后端分层、接口契约、兼容确认与验证仍按对应细则执行。

## 单一实现门禁

**同一业务流程默认统一走新实现。未经用户明确授权，禁止保留新旧两套实现。**

- 旧数据可能来自已废弃功能。发现旧数据时，先核实旧功能和数据是否仍需支持，再按[兼容处理原则](design.md#兼容处理原则)确定处理方式。即使用户确认要兼容旧数据，保留两套业务实现仍须单独获得双轨授权。
- 替换流程时，沿入口和调用链切换本次范围内的调用方，并清理已被替代的旧分支、入口、开关和仅服务旧流程的代码。需要扩展切换范围时，先说明影响并对齐方案。
- 通过版本、配置、数据形态或异常回退把请求分流到旧逻辑，属于新旧并存。确需兼容旧调用或数据时，先按[兼容处理原则](design.md#兼容处理原则)取得用户明确授权。获准后优先在入口转换旧格式，后续仍走同一套业务实现。确需保留两套时，要明确各自服务谁、何时退出以及如何验证。
- 评审从真实入口追踪调用链，核对是否还有旧路由、开关、分支或回退可以执行已替代的流程，以及旧代码是否已清理。发现未经授权的并存，先合并到新实现或清理旧路径，再通过评审。

## 实现原则

1. **做能完整解决问题的最小改动。** 先沿真实入口找到问题根因或负责该行为的模块，再从那里修改。以受影响的行为、调用方和依赖衡量改动范围，避免顺手重构、格式化、升级依赖或改变公开接口。必要的契约、状态分支和验证属于本次改动的一部分。
2. **同一条业务规则只有一个权威实现（DRY，Don't Repeat Yourself）。** 先查现有类型、常量、函数、组件和接口，语义一致时优先复用。只有当多处代码表达同一规则、业务变化时必须一起修改，才归并到负责该规则的模块。代码形状相似但职责不同、各自变化的逻辑可以保留独立实现。
3. **优先采用能直接读懂的方案（KISS）。** 让职责和数据流清楚，名称表达业务含义。减少无意义的转发、重复分支和隐式约定。函数拆分应让调用处更容易理解，或让一项职责更容易验证。避免靠压缩行数、缩短命名或堆叠条件来追求简短。
4. **只为已明确的需求增加设计（YAGNI）。** 沿用现有架构和依赖。新增层、接口、框架、配置项或通用组件前，先说明当前哪个调用方或约束需要它，以及现有结构为什么无法承接。未来用例还不确定时，先把当前实现写清楚，等需求出现再扩展。
5. **在统一实现中核对已有调用方依赖的行为。** 检查真实入口、受支持的输入、默认值、错误语义和已有数据。涉及部分失败、重试或并发时，说明如何保持状态一致。发现无法通过统一切换保留的行为时，按[兼容处理原则](design.md#兼容处理原则)确认切换或兼容方案。
6. **验证实际变化。** 优先利用已有检查和测试覆盖主路径及受影响的边界。用户或仓库要求新增测试，或现有测试会漏掉具体回归时，补能复现该问题的测试。测试范围随风险确定，目标端联调和验收按[整体验证细则](../03-delivery/verification-and-delivery.md)执行。

## 动手前对照已有实现

每轮代码变更都先确定真实入口和受影响的调用链，在仓内查找同层、同职责且最接近本次需求的实现，按改动范围完整读通相关层和调用方。不能只看单个相似文件就开始实现。

1. **逐层对照。** 后端按实际涉及的路由、DTO、UseCase、Service 接口与实现、Repo 接口与实现、事务、模型、Wire 装配、测试和共享契约查阅；前端按实际涉及的页面或组件、状态、数据访问、契约、样式与测试查阅。没有命中的层无需人为扩展。
2. **明确复用和差异。** 核对职责边界、接口与具体类型、构造与依赖注入、错误和事务处理、命名及数据约定；优先沿用仓内现有模式。相似实现不一致时先查明适用场景，选择与本次职责最接近的方式；确无对应实现时说明依据后按现有架构设计。
3. **动手前留下依据。** 在方案或对应阶段过程记录中写明本次对照的关键文件或调用链、准备沿用的模式、必要差异及原因；小改动可简要记录，不要求新建文档。参考不完整或仍有影响行为的关键歧义时，先补齐再修改。
4. **完成后沿同一调用链复核。** 检查各层职责、接口绑定和依赖装配是否一致，测试和契约是否覆盖受影响入口；对未按参考模式实现的地方核对理由，修正无依据的偏离。编译、单元测试通过不代替这项检查。

## 为接手人写注释

- **默认保留仍然准确的已有注释。** 重构、移动或拆分代码时，把仍适用的业务背景、约束和注意事项随代码迁移到对应位置。行为变化时同步更新注释。只有原说明已经失效、对应逻辑已删除，或信息已完整迁到更合适的位置时，才删除旧注释。评审时应能从 diff 看出删除原因或找到信息的新位置。
- **新增或修改关键逻辑时，主动补足接手所需的上下文。** 关键入口和导出接口按仓库惯例说明职责、调用条件和可观察的副作用。业务规则、特殊分支、执行顺序、重试或并发约束等从代码难以看出原因时，在对应位置写明为什么这么做，以及改动时必须保住的条件。发现本次触及的代码缺少这类说明时一并补上。
- **让注释解释代码之外的信息。** 注释放在它解释的函数、分支或字段附近，语言和格式沿用仓库约定。用简短而具体的说明，例如「支付回调可能重复投递。先用交易号去重，再更新订单状态。」简单赋值和直观条件由清楚的命名表达，避免逐行复述。

## 怎么写进方案和评审

- **方案**写明从哪个真实入口触发、修改哪个模块、复用哪段已有逻辑、怎样验证受影响的行为。增加抽象、依赖、配置或扩大改动范围时，补一句当前依据。小改动可直接写进「实施方案」，无需另建模板。
- **动手前**按[动手前对照已有实现](#动手前对照已有实现)逐层核对；字段改动还要对照相邻字段的命名、标签、序列化和默认行为。只有需求、既有契约或实际调用方明确要求差异时，才引入不同写法，并记下依据。
- **评审**沿实际调用路径看 diff。检查业务规则是否出现第二份实现、新增层是否有当前职责、异常和历史数据是否覆盖，以及每项改动是否对应本次需求或验收标准。逐处核对删除或移动的注释，确认有效信息仍能找到，并检查关键改动是否补齐接手所需的说明。
- **涉及序列化时**，用已有样例或实际输出核对字段名、空值和默认值。签发后能读回同一结构，只验证了读写能配合。发现 diff 改变了原有约定时，核对契约或调用方是否需要，清理无依据的差异再交付。
- **原则冲突时**，先满足业务正确性和既有行为约束，再选择影响范围小、阅读和维护成本低的方案。例如，两个入口共用同一业务校验时，应复用已有校验。两段流程只是写法相似时，可以各自保持简单。
