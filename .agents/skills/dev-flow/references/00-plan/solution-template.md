# 开发方案模板与表达规范

本文件规定开发方案的章节顺序、每章写法和图示标准。完整方案参考 [Superone MCP 方案案例](solution-example.md)，学习它先说明需求与使用，再展开模块、接口、数据和验收的表达顺序；案例里的业务事实、历史状态和技术选型以原任务为准。

专项和日常任务均在任务目录 `plans/` 下按主题写独立方案，任务 README 记录目标、状态和方案索引。跨端需求共用一份方案。**方案默认一篇写完整**，包括接口、数据表及可评审 DDL。用户明确要求拆分，或单篇过长确实影响阅读时，才将独立细节拆到附件，并在正文对应位置说明和链接。

## 一、整篇怎么组织

按下表顺序写，章节标题可因内容调整，阅读顺序保持从需求、使用到实现、验收。小改动可合并不适用的章节；有数据库、接口、跨端、权限或部署影响时，相应内容不能因篇幅省略。未涉及的内容明确写“不涉及”，未确定的内容集中列出，不虚构事实。

| 顺序 | 章节 | 读者要得到的答案 |
| --- | --- | --- |
| 1 | 需求与范围 | 谁需要什么，本次交付哪些目标，当前状态及待决定事项 |
| 2 | 整体方案 | 准备怎样实现，哪些现有能力被复用，涉及哪些系统 |
| 3 | 使用流程与图 | 用户如何从入口完成目标，业务与系统如何协作 |
| 4 | 任务拆分与实施顺序 | 每一步交付什么、依赖什么、如何验收、处于什么状态 |
| 5 | 功能模块设计 | 每个模块的入口、动作、处理、结果、异常与权限 |
| 6 | 接口与契约 | 请求、响应、鉴权、错误，以及调用方如何切换 |
| 7 | 数据设计与迁移 | 表、字段、索引、DDL、历史数据、执行与回滚 |
| 8 | 改动范围 | 每个仓库、文件或目录承担什么改动，哪些现有实现复用或替换 |
| 9 | 验收与验证 | 对每项目标，如何在什么环境操作、看到什么结果 |
| 10 | 风险与回滚 | 本次实际风险、失败影响、恢复步骤和需要决定的数据处置 |
| 11 | 落地记录 | 开发后回填实际变更、验证、部署和未解决项；开发前可省略 |

## 二、每章怎么写

### 1. 需求与范围

- 将目标写成可逐项核对的数字列表，每点以**加粗的短目标**开头，后接完整句子交代使用者、动作和结果。不要把多个目标压成一整段，也不要只列“组织、权限、接口”等名词。
- 列表之后分别标明**当前状态**、**已确定**、**待决定 / 待验证**。仅在有内容时写，明确每项决定影响什么。用户确认的需求、方案建议和代码实况分开写；用户尚未确定的判断不能写成既定规则。
- 写清本期范围及与本次交付有关的边界。对同一目标的背景、规则和后续动作放在一起，避免读者跨章节寻找主干。

示例格式：

```markdown
## 需求与范围

1. **创建并分享组织。** 组织者创建组织并生成邀请链接，受邀用户通过自己的账号加入。
2. **共享组织内容。** 成员可以查看组织内容，写入权限按已确认规则处理。

**当前状态**　说明已实现和待完成的部分。

**已确定**　列出用户明确确认的规则。

**待决定**　写清问题、可选方案与对功能或数据的影响。
```

### 2. 整体方案

用编号列出关键实现方向，每点以**加粗动作或决策**开头，再说明复用的入口、参与系统和职责。例如“复用现有扫码登录”“在现有服务增加组织能力”。按用户理解顺序组织，覆盖范围内所有主要能力；不要在这里堆字段、表结构或无上下文的文件清单。

### 3. 使用流程与图

先用一到两段说明真实角色如何开始、经过什么步骤、最终得到什么。区分不同角色和不同客户端；失败处理在模块或图中展开。紧接着放图和原稿链接，使文字、图、后续模块能互相对照。

涉及多角色业务交接及跨系统处理的完整方案，默认各画**一张业务泳道图**和**一张系统时序图**，两张都覆盖本次需求的完整主流程与必要分支，各自从业务和实现角度表达。简单需求没有相应交接或系统交互时，可只用文字或选用一种图，说明选择依据。图实在无法兼顾完整性和可读性时先扩大画布、调整布局与合并重复路径；需要拆图时先遵循用户明确要求，并在方案中说明分图范围，不悄悄按功能把总图拆散。具体制图规则见下方第四节。

### 4. 任务拆分与实施顺序

按依赖顺序列子任务，一项应能独立交付和验收，不按代码文件机械拆分。每行的交付物以**加粗的动作**开头，写清需要改出什么；前置依赖说明前一任务、授权或环境；验收写操作与可观察结果；状态使用待开始、进行中、已完成或具体阻塞，不提前写已通过。

| 顺序 | 子任务与交付物 | 前置依赖 | 验收方式与结果 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | **建立业务入口。** 写明交付内容 | 写明依赖 | 在指定环境执行操作，写明预期结果 | 待开始 |

### 5. 功能模块设计

按用户理解或执行顺序写 `### 1. 模块名称`、`### 2. 模块名称`。每个模块先用一小段说明用户要做什么、完成后得到什么，再用有序列表写**动作 → 系统处理 → 结果或错误**。每点以**加粗短句**开头，说明真实入口、身份、调用链、数据状态和需要的失败处理。仅列与该模块有关的步骤，不重复抄接口表。

根据实际影响，明确角色权限、数据归属、校验、状态变化、重试、并发、幂等、部分失败及数据隔离。写明复用的代码或机制及依据；方案假设或尚未验证的选型单独标记，不借案例推断业务规则。涉及页面时补入口、各状态和目标端，必要时按前端细则提供原型与状态矩阵。

### 6. 接口与契约

逐项列出实际接口或工具的**方法与路径 / 工具名、用途、请求字段及必填规则、响应字段、鉴权和错误语义**。多个入口共享业务逻辑时说明它们如何映射到同一 Service。写清默认值、分页、排序、枚举、版本和受影响调用方，链接唯一事实源。复杂请求可给小而真实的请求、响应示例，示例数据标明为示例，不称为实测。

### 7. 数据设计与迁移

逐表说明职责、字段类型、NULL、默认值、comment、主键及索引对应的查询或唯一约束；数据库变化给出正文内可评审的 DDL / DML。写清目标环境和版本需核对的部分、历史数据含义、执行前检查、停写或切换顺序、验证、失败恢复和回滚时的数据处理。SQL 草案、已执行 SQL 和结果要区分。按后端字段规范核对真实表模型、同类迁移和目标库结构。

### 8. 改动范围

按仓库或层级列出已定位的**文件 / 目录、职责、复用点和调用链**。涉及替换时列出需切换的入口、客户端、契约、存量数据和需清理的旧路径。未定位的文件明确写待核，不用泛泛的“修改后端”。

### 9. 验收与验证

每个已确认目标至少有对应场景。每行写场景、实际操作、可观察的预期和环境；覆盖主要失败、权限、并发、历史数据及受影响调用方。明确本地编译 / 测试与真实客户端和目标服务联调各自覆盖什么。结果只记录实际执行的证据，未执行写待验证。

| 场景 | 操作 | 预期结果 | 环境 |
| --- | --- | --- | --- |
| 主要使用场景 | 描述谁做什么 | 描述可观察的结果 | 本地或具体目标环境 |

### 10. 风险与回滚

只写本次实际存在的权限、数据、兼容、切换或外部依赖风险。按失败发生时的处理顺序说明停写、备份、代码 / 数据回退、校验以及恢复服务；数据保留或处置未决定时明确标出。上线、数据库执行和发布授权按现有流程处理。

## 三、如何分点、编号和强调

1. **标题层级。** 文档一个 `#` 标题，主要章节使用 `##`；功能模块使用 `### 1. 模块名`，模块内步骤从 `1.` 开始。章节编号用于模块顺序，不强制给每个 Markdown 标题加编号。
2. **数字列表。** 需求目标、整体方案、模块步骤及有顺序的动作使用数字列表。每点使用 `1. **短动作或结论。** 完整说明`；点名动作、对象或结果，再说明条件与影响。同一列表每点承担一个主要意思。
3. **无序列表与表格。** 无先后关系的规则可用短横线；多项数据需要横向比较时用表格，例如接口、数据结构、任务拆分和验收。表格不能替代对业务流程、失败路径和设计原因的说明。
4. **加粗。** 对列表的短标题及真正需要快速定位的状态、决定和关键限制加粗；正文用正常字重。不要整段加粗，不为每个术语加粗。`当前状态`、`已确定`、`待决定`等状态标签可加粗，信息以自然句子跟随。
5. **准确标记状态。** 使用“已确认”“建议”“待核”“已验证”表达不同状态；每个已验证结论写环境、操作与出处，避免把草案或本地模拟写成目标环境通过。图内也要与正文一致。
6. **引用与代码。** 路径、接口名、字段和命令使用反引号；引用工作区文件时使用相对 Markdown 链接。示例标注为示例，敏感凭证不进入文档。文档用中文，术语保留原名。

## 四、如何画图

### 业务泳道图

- 一张图按**业务角色或责任方**划分泳道，表达用户从入口到结果的完整业务流程。角色动作、系统受理、判断条件、成功与失败分别落在负责的泳道；流程从上到下，标出跨角色的交接和必要分支。
- 用动作描述业务，例如“生成邀请链接”“成员加入组织”“按分类查找 Skill”；技术事务、数据库字段和内部函数留给时序图或文字。单独节点未连到主流程时，要说明它是并行入口，不能让读者猜测先后关系。
- 组织者与成员只是角色不同，同一角色在不同阶段变化时在图中写清。对可选动作、不同类型和失败分支使用明确条件，不将这些路径误画为所有用户必须依次执行。

### 系统时序图

- 一张图按**实际系统参与方**排列，例如目标客户端、API / MCP 入口、业务服务、数据库或外部服务。从上到下画请求和响应；实线表示请求 / 调用，虚线表示响应。图前注明线型含义。
- 展示本次需求的完整处理路径及关键校验、事务、数据状态、失败结果和客户端后续动作。用分支或标注区分可选场景、不同客户端及失败条件，避免把并行或独立场景误写成固定时间依赖。不得把未实现的建议标成已有系统行为。

### 统一视觉和文件约定

- 默认使用 Draw.io，保留可编辑 `.drawio` 原稿及嵌入方案的 `.drawio.png` 预览。先确定流程、角色和条件，再选合适的手工布局或生成方式；自动布局只是起点，必须人工核对并调整，不能把默认样式当成完成。
- 默认参考案例的浅色视觉语义。泳道标题用浅蓝 `#E0EBFA`、浅灰蓝 `#E8EEF4`、浅绿 `#DEF0E7` 区分责任方；普通操作白底 `#FFFFFF`、边框 `#8AACC9`；判断用浅黄 `#FFF2CC` 和金色边框 `#D6A13A`；成功 / 完成用浅绿 `#DFF0E5` 和 `#7AB595`；失败 / 拒绝用浅红 `#FAE3E1` 和 `#D97972`；连线用蓝灰 `#536E8A`。颜色辅助语义，节点文字和分支标签也必须说明含义，不靠颜色单独传达。
- 同一文档的两图沿用相同字体、颜色和线条语义。文字保持中文，系统术语使用真实名称；字号在文档宽度下可读。若用户或项目已有指定视觉规范，优先遵循其要求。
- 箭头先有明确源节点与目标节点，主流程尽量水平或垂直。避免线条穿越节点、遮挡文字、分支标签重叠或无意义折返；必要时移动节点、增加间距或设置连接点。不同泳道间的交接必须能追踪来源和去向。
- 在方案中分别写图的作用、角色及特殊约定，先链接可编辑原稿，再嵌入预览。修改方案中的角色、流程或权限时同步修改对应图和导出图。

### 图示交付检查

逐图打开导出的图片，以实际显示尺寸核对：

1. 所有需求主流程和重要失败分支可从图中找到；业务泳道图与系统时序图各自覆盖完整范围，图文一致。
2. 每条线有正确方向，连到正确角色和节点；请求与响应、可选流程、判断的通过和失败能区分。
3. 检查文字裁切、线穿节点、文字重叠、连接点偏移、无意义短折线、交叉和不必要的大面积留白；发现问题后改原稿、重新导出、再次查看。
4. 原稿和图片均存在、链接有效；用户打开 `.drawio` 能继续编辑，不把一张不可编辑的截图冒充原稿。

## 五、交付前逐项核对

- 需求、整体方案、图、任务拆分、模块、接口、数据和验收能逐项对应；核心目标不存在只有标题、缺少处理细节的情况。
- 一篇方案即可从需求读到实施与验收；确需附件时，正文链接准确且能独立理解关键取舍。
- 已确认、建议、待核和已验证没有混用，环境、调用方和外部条件如实标记。
- 编号、加粗、表格、代码块和链接按本规范排版；图已实际查看，原稿与预览一致。
- 涉及代码、库表、权限、客户端或部署的设计达到 [设计门禁](design.md#门禁)，未达到时明确列出缺口，不声称可进入开发。
