# 功能与系统设计

## 设计覆盖

涉及代码改动时，按[代码方案与实现原则](code-design.md)选择实现路径，并在「实施方案」写清复用点和必要的取舍。

按需求规模填写；小改动可以简写，但必须覆盖本次实际影响的部分：

- 功能设计：用户角色、入口、主流程、关键状态、异常与回退、权限和边界。
- 系统设计：涉及的仓库与模块、职责边界、调用/数据流、依赖方向、平台适配位置。
- 数据设计：实体、字段、索引、默认值、历史数据兼容与迁移方式。
- 接口与契约：method、path、Req/Resp、鉴权、错误语义、唯一协议事实来源和客户端同步方式。
- 前端设计：原型、信息架构、主次 CTA、状态矩阵、数据层与页面边界；命中品牌项目时补品牌约束。
- 验收与交付：可判定的功能/回归验证、部署环境、回滚与风险。

不适用的部分注明原因，避免为了填表虚构系统组件或兼容对象。

## 可复用基础能力评估

每份功能方案都要检查本次是否需要使用或扩展已有基础能力，并在系统设计、实施方案或验收中给出结论；不适用时简短说明原因，不为满足清单而强行接入。

- **用户行为埋点。** 当功能涉及用户操作、关键转化、功能使用情况或后续产品分析时，评估复用现有埋点能力。需要埋点时，方案列出事件触发点、事件名、项目/业务/功能标识、必要属性、身份来源和验收方式；身份应由后端从已验证凭证取得，不能信任客户端传入的身份字段。若不需要，说明本功能没有需要观测的行为或指标。
- **HTTP + DB autotest。** 当后端接口会创建、更新、删除或查询持久化业务数据时，评估复用业务仓 `autotest/` 的真实 HTTP 调用与数据库断言能力。方案按业务用例列出独立 `Test...` 方法、接口操作、关键 DB 断言、test 环境和 fixture 清理/保留方式；先扩展现有测试包和运行入口，不另建并行测试框架。纯展示、无后端状态变化或无法安全连接目标环境时，说明不适用或待验证原因。
- **跨项目复用。** 后续项目应先核对现有埋点接口和 autotest runner 是否适配，再决定直接复用或补齐差异；不要因当前首个接入项目的字段、库表或命令不适配，就默认复制一套基础设施。

## 业务规模与设计复杂度

设计前先核对目标产品的真实用户规模、请求量、数据量和性能目标；已知规模写入方案或任务记录，没有数据时标记为假设，不按大型互联网服务的默认规模设计。

前后端 MVP 默认采用宽约束、快开发方式：先覆盖已确认的主流程和必要失败处理，沿用项目风格，不为未发生的风险增加严苛校验、复杂保护或扩展架构。具体实现遵循[实现范围变更门禁](code-design.md#实现范围变更门禁)和[MVP 优先与宽约束](code-design.md#mvp-优先与宽约束)。

当前已知产品基线：鹅懂个啥（`uni-gknow`）日活约 100。涉及该小程序及其后端功能时，默认优先采用直观的调用链、普通数据库查询、必要索引和适量分页，避免仅为理论扩展性引入缓存层、消息队列、分库分表、复杂 SQL、预计算或多层抽象。业务要求、已观测到的瓶颈、明确的可靠性目标或数据一致性要求需要这些机制时，再按实际证据设计。

日活基线只用于控制实现复杂度，不降低认证授权、数据正确性、错误处理、隐私或可维护性要求。涉及明显高峰、增长预期或外部服务限制时，记录具体约束并据此调整设计；不要只用日活数字推断并发峰值。

## 方案产出

按 [开发方案模板与表达规范](solution-template.md) 的章节、分点、图示和交付检查撰写，按改动范围裁剪。专项和日常任务的方案统一按主题放在任务目录的 `plans/` 独立文档中，由任务 README 索引。跨端任务共用一份方案。

写作前先判断模板每项适用与否，并沿现有代码、契约和任务记录查证可自行确定的事实。适用项必须写出可评审内容；不适用项写明原因。图示、接口、DDL、调用链或验收有缺口时，先完成不依赖用户决策或外部条件的工作，不以「待补」收尾，也不把章节齐全当成方案完成。

方案表达服务于实现和评审，不为交付文档本身增加产物。涉及多角色协作、跨端状态或复杂调用顺序时，再补能澄清问题的流程图或时序图；简单 MVP 和局部改动用文字、接口样例或短清单说明即可，不强制画图。

涉及数据库变更时，先读取 [后端字段与 DDL 规范](../01-backend/field-design-norms.md)，对照目标仓库模型和同类迁移，提供可评审的 DDL 或 SQL 链接及数据迁移说明；涉及接口时明确方法、路径、请求、响应、鉴权、错误和受影响契约。验收说明结果，验证写操作、环境与预期，简单场景可以合并。

按依赖拆分可顺序完成和验收的子任务，说明交付物、前置条件和验收方式。简单需求可以作为一个子任务。

## 兼容处理原则

- 同一业务流程按[单一实现门禁](code-design.md#单一实现门禁)设计。替换流程时列出要切换的调用方、要清理的旧路径，以及存量数据如何接入新流程。没有兼容对象时，兼容性测试注明「不适用」。
- 已发布版本、存量数据、外部调用方和平台差异是核查线索。即使有旧数据，相关功能也可能已废弃。先核实旧入口、调用方和数据是否仍需支持。已确认废弃且数据无需继续使用时，按新流程设计。状态不明确时，说明受影响对象和切换或迁移办法，由用户明确决定是否需要兼容。任何兼容实现或数据操作都要说明兼容对象、写入内容和影响范围，并在动代码或脚本前获得用户明确确认。
- 需要新旧实现并存时，单独写清原因、适用对象、分流条件、验证方式和退出条件，并取得用户对并存本身的明确授权。一般方案确认、「直接做」和全自动模式均不能代替这项授权。

## 门禁

以下任一项不满足，不得进入开发与迭代阶段（03）：

- 任务目的未写清。
- 改动范围未落到文件级别；涉及库表时未落到表级别。
- 涉及数据库变更时，表、字段、索引、默认值、可评审的 DDL 或 SQL 链接，以及历史数据和迁移处理未明确。
- 涉及接口变更时，方法、路径、请求、响应、鉴权、错误及契约影响未明确。
- 涉及页面时未列明状态分支。
- 验收标准不可判定。
- 子任务的依赖、交付物或验收方式未明确。
- 适用的模板内容或图示缺失，或图示尚未按模板检查。

提交用户评审前，对照模板逐项核对内容、图示和文件链接；有可自行补齐的缺口就继续完成。只有用户明确要求看半成品，或具体外部条件 / 必须由用户决定的事项使其无法完成时，才交付未完成稿：说明已做内容、准确缺口、阻塞原因及影响，不称为满足门禁或请求整体方案确认。等待答复期间继续不依赖该答复的工作。不得把通用的「待核」「待补」当作阻塞理由。

方案未确认前，不改代码、不执行 DDL/DML、不推进分支。

## 工作模式

### 方案确认模式

默认模式。用户表达「先出方案」「确认后执行」「评审方案」时使用。产出方案文档后停下等确认，不进入实现。

前端方案至少包含：产品原型判断、状态矩阵摘要、文件级方案、资产主权决策、品牌一致性注意点、验证命令。

### 全自动模式

用户表达「直接做」「自动完成」「不需要确认」时使用。一次走完方案、开发、执行、验证，但仍有两条硬约束：

1. 方案文档照常产出，作为过程记录和回看依据。
2. live 环境 DDL/DML 必须用户显式授权，不得由全自动模式推断。

全自动模式下，数据库变更在 `test` 环境执行并验证。执行 DDL 前须取得用户对该次 DDL 的确认，用户明确说「只生成 SQL / 不执行数据库」时仅生成 SQL。

前端部分默认跑 `npm run type-check`；涉及平台差异时补目标平台 build。

## 最终输出格式

- 需求理解：一句话。
- 方案文档路径。
- 改动范围：按仓库、库表、接口、契约、页面分组。
- 实施路径：涉及哪些后端、前端、协议与验证工作，哪些不适用及原因。
- 产品完整性风险：只列真实缺口，例如状态分支缺失、外部依赖残留、品牌一致性未收口。
- 待确认项：只列真实阻塞或需要用户决策的点。
