# 开发流程

这是 dev-flow 唯一的流程入口 skill。开发需求由本 skill 负责阶段推进，后端、前端、设计、验证细则按需从 references 读取；不要把实现阶段再次拆成多个入口 skill 组合触发。

## 动手前与交付前

1. **改代码前，找同职责实现。** 先看目标业务仓 `AGENTS.md`。沿本次真实入口读通受影响的层，在已有方案或过程记录中简记「对照文件 → 复用方式 → 必要差异」。新接口须对照路由、参数与错误处理、UseCase、Service、Repo 和注入中实际涉及的部分。已确认方案直接进入实现时，也先核对这条记录与当前代码。小修只查受影响的部分。 [代码设计细则](references/00-plan/code-design.md#动手前对照已有实现)
2. **MVP 优先，约束从宽。** 前后端采用能满足当前业务的最小完整实现，沿用项目现有分层和风格。只加入业务正确性、安全和已证实运行条件所需的校验与保护；不为假设场景增加严格字段限制、额外限流、复杂回退、抽象层或通用机制。新增约束会影响客户端兼容或用户行为时，必须有明确需求或具体证据。 [MVP 实现原则](references/00-plan/code-design.md#mvp-优先与宽约束)
3. **实现范围必须有依据。** 只做用户明确提出或已确认方案包含的改动。不要自行添加重构、通用抽象、兼容策略或其他架构调整。若实现中认为必须改公共层、共享入口、基础上下文、全局配置或既有接口行为，先暂停这部分，向用户说明为什么现有结构无法承接、改动收益、影响范围和更小替代方案，等用户明确选择后再改；已授权的其余工作可继续。用户说「开始实现」只授权已对齐的需求和方案，不自动授权扩展范围。 [代码设计细则](references/00-plan/code-design.md#实现范围变更门禁)
4. **跑集成测试前，确认依赖环境。** 先核对测试命令实际连接的数据库、Redis 等依赖及其配置来源，再用项目的 test 环境验证。将测试启动、编译检查和目标端联调分开记录。 [整体验证细则](references/03-delivery/verification-and-delivery.md#后端接口集成测试)
5. **交付前，按同一条调用链看 diff。** 核对共享入口是否被绕开、职责是否落在正确的层、注入和契约是否跟上。识别超出已确认范围的改动并撤回或先取得用户决定。针对实际行为跑检查，编译通过只作为编译证据。

## 流程

| 阶段 | 目标 | 主要产物 | 退出条件 |
| --- | --- | --- | --- |
| 00 任务初始化 | 绑定或建立任务上下文，创建基础文件并登记 | `task/dev-flow/{任务编号}_{主题}/README.md`、`handoff/`、`process/`、任务登记 | 任务范围与目录明确 |
| 01 需求理解与沟通 | 理清目标、约束、边界、受影响对象；与用户对齐真实需求 | 已确认的需求理解与范围 | 关键歧义已解决，用户认可理解 |
| 02 功能与系统设计 | 形成可执行的产品、数据、接口、系统和验收设计；评估埋点与 HTTP + DB autotest 等可复用基础能力 | 任务目录 `plans/` 下的独立方案文档 | 设计、影响范围、基础能力适用性和验收标准满足门禁；默认等待用户确认 |
| 03 开发与迭代 | 按方案实现；运行针对性检查或预览，收集反馈并继续修改 | 代码、契约、过程记录 | 反馈收敛，目标和验收标准达成 |
| 04 部署、总结与交接 | 按授权推进分支或部署，核验结果，回填总结并写 handoff | 部署/验收结论、过程记录、最新 handoff | 结果可追溯，后续动作明确或任务关闭 |

按需求裁剪阶段；需求理解、方案和实现后的验收构成基本闭环。纯前端或纯后端任务只做命中的部分；缺陷修复先明确复现条件与验收结果，设计可以保持轻量。

## 入口路由

1. 读取工作台 `AGENTS.md`、`task/registry.md`，再按 `wb-router` 建立业务仓和任务上下文。检查最近任务，优先复用同一需求链条的目录；确属独立目标时才新建。用户明确要求建目录时直接执行。
2. 设计方案统一放任务目录 `plans/` 下的独立文档，任务 README 保留目标、状态和方案索引。新建任务时参考 `wb-router/references/task-readme.md` 初始化 `README.md`、`handoff/`、`process/` 并更新登记；目录创建和登记完成后，按 `wb-handoff` 的「会话绑定任务」规则将当前会话标题改为任务目录末级名称。进入既有任务时先读 README 和最新 handoff，并按同一规则处理会话绑定与改名。
3. 按当前阶段和改动范围选择资料。完整目录、阶段索引和路径变更约定见 [`references/README.md`](references/README.md)。仓库路径、技术栈、命令、分支或部署信息需要时调用 `dev-flow-tools-repo`。
4. 每阶段结束时按任务目录的 `process/` 记录结论，遵循 `wb-handoff/references/process-template.md` 的格式与边界；只有需要跨会话续接、中断交接、任务收口，或用户明确要求时，才写或更新 handoff 并调用 `wb-handoff`。

## 需求和设计门禁

先用一句话复述需求和当前理解，再针对会改变行为、数据、权限、兼容性或验收结果的缺口向用户沟通。可由现有实现安全确定的细节，说明依据并继续，不逐项询问无关偏好。需求变化时更新任务 README 和改动范围。

**写方案的入口要求。** 用户要求写、修改或评审开发方案时，先读取 [方案模板与表达规范](references/00-plan/solution-template.md) 和 [设计细则](references/00-plan/design.md)，按模板组织实际方案，而不是仅把章节名称写进草稿。交付或要求用户确认前，逐项执行模板末尾的交付检查；适用的图、接口、数据和验收等缺项要先补齐，不能靠标记「待补」或「后续完善」代替。真实外部阻塞或必须由用户决定的内容除外，具体处理见设计细则。轻量任务可按实际范围裁剪，并说明不适用的原因。

默认采用方案确认模式：方案达到门禁后停下等用户确认，再进入实现。用户明确要求直接做、自动完成或本轮完整交付时，可按全流程执行；live 数据库写入、生产部署或公开发布仍需符合对应工具与工作台授权规则。

不得在关键需求未明、方案范围不清、验收不可判定时开始业务代码或数据库写入。设计深度按风险和改动范围调整；涉及数据、接口、权限、页面状态和多端契约时，写清影响与验证方式。

**单一实现是硬门禁。** 同一业务流程默认把本次范围内的入口和调用方统一切到新实现，并清理被替代的旧路径。发现旧数据时，先核实旧功能是否仍需支持。只有用户明确确认需要兼容，才可引入兼容逻辑。新旧实现并存必须另有用户对双轨的明确授权。「直接做」、一般方案确认和同意兼容都不能代替双轨授权。见[兼容处理原则](references/00-plan/design.md#兼容处理原则)。

## 验证边界

- 数据库相关开发验证使用项目现有的开发测试库，不自行新建或启动临时数据库。需要 DDL 且尚未获得该次确认时，先只读核对目标库并准备具体 SQL、影响与验证方式，向用户确认；等待期间继续不依赖迁移的工作，不得换库绕过确认。用户已明确确认具体 DDL 时直接执行，不重复询问。
- 涉及接口和后端集成时，先设计业务用例，再启动本地真实服务并通过接口验证完整链路；也支持部署后使用 test 环境接口执行。用例和环境要求见[整体验证细则](references/03-delivery/verification-and-delivery.md#后端接口集成测试)。
- 不新建 H5 页面或模拟应用来验证其他目标端的功能与界面；H5 本身是正式交付目标时直接验证真实产品。禁止以模拟后端或本机替身冒充实际服务的联调结果。
- 需要验证跨端、实时通信或后端交互时，使用用户实际部署的目标环境和目标端。实际服务尚未部署或真实链路暂不可用时，停在待联调状态，向用户说明需先部署；未经授权不自行部署，也不以 H5 或模拟服务替代。
- 类型检查、编译及独立单元测试可作为开发检查，明确说明覆盖范围，不能据此宣称目标端或真实服务验收通过。

## 开发反馈循环

实现按依赖和改动范围推进，不要求每个功能都走完整后端/前端清单。每次有可评审结果时运行必要的针对性检查、预览或演示，再结合用户反馈修改：

`实现 → 检查/预览 → 用户反馈 → 修改 → 再检查`

反馈改变需求目标或系统边界时，回到阶段 01 或 02 更新理解和方案后再继续；只是实现细节或视觉调整时留在阶段 03。保持每轮改动聚焦，过程结论追加到同阶段记录。不要因加载某个细则就自动扩大任务范围或做无关重构。

## 部署与收口

部署前核对验收标准、目标环境、变更分支、数据库操作、回滚办法和用户授权。按 `dev-flow-tools-repo` 的实际命令执行；命令成功后核对目标环境或发布状态，不能把退出码当成部署验收。

最后将实际改动、验证结果、部署状态、未解决项和回滚信息回填任务方案，更新任务 README 索引，再按 `wb-handoff` 写可执行的下一步。未部署时明确记录阻塞和原因。任务完成后更新 `task/registry.md` 状态。

## 最终回复

简要报告需求理解、任务文档、改动范围、实际验证和部署状态；列出还需用户决定或外部条件阻塞的事项。路径和结论以实际文件与命令结果为准。
