# 写作风格与公共规则

本 skill 是 bn 族写作规则的统一维护入口。`bn-tools-edit-flow` 负责创作推进和事实核查，本 skill 约束表达方式；`bn-tools-format-flow` 保留对外文章模块并执行视觉排版。

## 已确认的表达方向

- 口语化，像和朋友把一件事聊清楚，使用具体、日常的表达。公众号默认开头自我介绍为「hello，这里是豆小匠的笔记。」；可根据文章主题自然微调，规则见 [文章公共模块](references/article-modules.md)。
- 需要说明数量关系时，用清楚的算账帮助理解，不拿数字装饰观点。先算账是当前投资文章可沿用的切入方式，不强制所有文章都这样开头。
- 正文只写对读者有用的信息，直接进入主题；不加入免责声明、空泛铺垫或重复提醒。风险与免责说明集中写在单独的置顶留言里。
- 保留分析中的分寸，不把假设写成确定结果，不用「熬到某一年就必然爆发」等说法推动读者采取行动。
- 分段、编号、加粗按内容需要使用；不强制四段结构、固定金句、名人引语或行动号召。

## 改稿时的通用检查

把以下内容作为改稿时的判断方法，按文章实际情况取用；它们不是每篇文章都要逐项完成的清单，也不规定文章结构：

- 先看原稿或用户材料里最重要的信息和表达节奏，尽量保留有用的部分，不为了“像公众号文章”而重搭骨架。
- 读者为什么会关心这件事，可以在开头用一句话点明；只有确实能帮助读者进入主题时才加，不强行制造收益承诺、悬念或共鸣。
- 检查有没有重复解释、空泛铺垫和与主题无关的内容；删减后仍要让关键事实、条件和逻辑关系说得明白。
- 新增解释要能帮助理解，并与已有事实和用户观点一致；不为扩写而扩写，也不把推测补成结论。
- 结构、篇幅、语气和收尾都根据本篇材料与用户要求决定。步骤、问答、叙述等形式均可使用，不设默认模板。

## 免责声明模块

免责声明统一放在置顶留言，不放进文章正文。写作和排版时将正文稿与置顶留言作为两个独立交付物，避免把免责声明或客套铺垫混进正文。模块规则和题材模板见 [文章公共模块](references/article-modules.md)，起草或检查时读取。理解论证必需的事实、条件和计算口径仍放在正文对应位置，完整核算依据放主题 source/。

## 使用与规则更新

1. 起草、改稿前读取本 skill，按当前用户要求应用相关规则；仅讨论主题时，不强制生成文章模块。
2. 本轮明确要求优先于这里的默认约定。某一篇的临时调整只记在该主题，不自动扩成全局规则。
3. 用户说「以后统一」「以后都这样」或明确要求修改风格规范时，更新本 skill 或相关 reference；编辑、排版等 skill 只保留调用入口，避免多处维护同一套细则。
4. 新规则要有用户指令或明确反馈依据。Agent 自己提出的建议、待确认草稿中的写法，不自动视为已经认可的风格。
5. 用户修订或撤销旧规则时直接更新有效规则，变化依据留在任务 process/；不把每轮反馈累积成越来越长的写作流程。

## 当前适用范围

用于 beannote 的公众号内容，不修改工作台技术文档的写作方式。暂不预设账号人设、字数、标题模板或具体产品的固定推荐；需要时按用户后续确认补充。
