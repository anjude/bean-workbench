# skill 族群阶段化重构

用于把「一堆编号平铺的 skill」重构成「按阶段推进的流水线」。工作台 2026-08-29 用这套流程做了三次：先把 `be-*` 后端族从 8 个平铺 skill 重构为四阶段 + 工具层，再把 `be-*`（8 个）与 `fe-*` 前端族（11 个）合并成 `dev-flow-*` 跨端族（21 个），最后把 21 个合并精简到 18 个。

## 什么时候需要重构

出现以下任一信号，说明编号只换了名字，流水线语义还是平的：

- 族里有一个明显过重的总控（超过 150 行，同时承担上下文、模式判断、编排、模板、输出格式）。
- 需求进来时没有成文的入口：不知道该先做什么、产出什么、什么条件下才允许动手。
- 同一份项目约定（目录位置、分支语义、命令）被多个 skill 各抄一遍。
- 某些能力会被多个阶段调用，却硬塞进了某个阶段编号里。
- 两个族群要合并，但各自的阶段语义对不上。

## 重构六步

### 1. 定阶段

按一次任务的推进顺序划阶段，不是按技术分层划。阶段号从 `00` 起。

判断标准：每个阶段要有明确的进入条件、产物和退出条件。能跳过的阶段才说明切对了；如果一个阶段永远不会被跳过，它可能和相邻阶段该合并。

典型四阶段：方案设计 → 后端开发 → 前端开发 → 整体验证。

跨族群合并时，先定目标族群的四阶段，再给被合并的族群出一张对齐映射表，不要两边同时改。

### 2. 拆总控

总控里的内容按去向拆三处：

| 内容 | 去向 |
| --- | --- |
| 共享上下文（目录约定、分支、技术栈、命令） | 工具 skill，`{前缀}-tools-project-context` |
| 需求理解、方案产出、阶段派发 | 阶段 `00` 的入口 skill |
| 各阶段的具体执行逻辑 | 对应阶段的 skill，不要留在总控里 |

拆完删掉总控。编排职责交给阶段 `00` 入口：它在方案确认后按改动范围派发下游 skill，不需要的阶段跳过。

### 3. 建工具层

横切能力命名 `{族群前缀}-tools-{能力后缀}`，不占阶段号，供所有阶段调用。

识别方法：如果一个能力在方案设计、开发、验证阶段都会被用到，它就不属于任何阶段。常见的是项目上下文、只读排查、分支推进/部署。

工具 skill 要写清边界，尤其是读写边界：只允许读的工具必须明确列出禁止的语句类型，并指回负责写操作的那个 skill。

### 4. 重排编号

编号规则：`{族群前缀}-{阶段号}{阶段内序号}-{能力后缀}`，`xx00` 留给阶段入口，具体 skill 从 `xx01` 起按执行顺序排。

**注意循环占用**：新编号可能已被其他待移动的 skill 占着。必须按拓扑序先移走占位者。

例：`A(0001)→0101`、`B(0101)→0103`、`C(0103)→0105`。正确顺序是 `C→0105`、`B→0103`、`A→0101`。目录重命名按此排队；文本替换无此问题。

文本替换用一次性正则扫描（`re.sub` 配合映射函数），不要逐条 `str.replace`，避免输出成为后续规则的输入。

### 5. 合并精简

族群稳定后做一次收敛。**合并优先于拆分**：数量膨胀通常不是因为缺 skill，而是把一个连贯动作切成了两三个文件，agent 每次都要连着读。

判定该合并：

- 两个 skill 的执行顺序永远相邻，且 B 的输入就是 A 的输出（设计 → 产出、落地 → 装配）。
- 单个 skill 正文只有几十行，去掉 frontmatter 和交叉引用后没剩多少实质约束。
- 触发条件高度重合，用户很难判断该调哪个。

不该合并：

- **读写边界**：只读排查和写操作必须分开，合并会让安全约束失效。判断标准：合并后文档里是否出现「本文件只做 X，禁止 Y」——有，就拆开。
- **带独立资产的特化层**：品牌规范、图标库这类带 `references/` 的 skill，合并进通用 skill 会把资产目录弄乱。保留独立，在通用 skill 里写「命中 X 时叠加 Y」。
- **正文超过 300 行的**：再往里塞会拖慢每次加载，宁可拆。

合并做法：以执行靠前的那个 skill 为主体，把被合并的内容作为章节并入，章节用「一、二、三」编号区分职责；合并后重排该阶段内序号，不要留空洞。合并掉的编号不复用。

### 6. 同步引用与文档

改完编号要同步：

- 所有 `SKILL.md` 的 `name` 字段与正文交叉引用。
- `AGENTS.md`：命名格式、阶段划分表、「当前 skill 编号表」。
- `docs/workspace.md`：命名格式与原则。
- `~/.agents/skills/wb-0001-router/references/business-generation-checklist.md`：skill 组合按新阶段重排。
- `task/registry.md`：路由提示与热任务登记。
- `script/check-workbench.py`：清单里的必需文件路径，新增或改名 skill 后同步进去。
- `.workbuddy/memory/MEMORY.md`：长期记忆里的编号体系段落。

skill 实体在工作台仓库里，`make commit` 会一起提交，不需要单独操作。

## 踩坑

- **脚本会误伤历史叙述**。全仓替换分不清「可执行的引用」和「历史文档里提到旧名」。设计文档的背景段、长期记忆的旧名对照表、`task/` 下的历史迁移清单，都要先排除、事后手工重写。判断标准：这句话是在描述过去发生了什么，还是在告诉 agent 去调用谁。
- **内容不能只换名字**。工具 skill 要写准，必须去业务仓查实际的 Makefile、脚本和命令，别凭记忆推测。踩过的例子：某个 push 脚本其实在临时 worktree 里合并，本地未提交改动不会带进去；`make test` 等价于带 `-short` 的测试；迁移脚本根本没有只读查询的 action，只读排查得走数据库客户端直连。
- **老 skill 里「本 skill 自包含，不依赖知识库目录」这类开头**，是重复抄上下文的历史产物。重构时统一改成指向工具 skill。
- **交接点要显式写出下游**。流水线最后一个 skill 容易漏掉指向下一阶段，导致链路断在末尾。
- **合族后会出现同名 skill**。前后端各有一个 `api-flow` 是常事，靠阶段号区分即可，改后缀反而割裂历史；但要在编号表里把职责写清楚。
- **工具 skill 会从单仓变成多仓**。合族时原来只服务一个仓的 project-context 要扩成按仓分段的速查表，写入前先去业务仓核对真实目录和命令，别把旧文档里的过期路径抄进去。
- **悬空引用扫描要区分活跃文档和历史记录**。活跃文档（`AGENTS.md`、`docs/`、`task/registry.md`、各 `SKILL.md`、长期记忆的正文）必须全部改成新编号；历史任务文档（`task/YYMMDD_*/README.md`）和长期记忆里的「旧名对照链」要刻意保留旧名，否则以后查不到演进过程。扫描脚本先排除这两类，再判断剩下的告警。
- **批量重命名会撞编号**。一次性 mv 到 `tmp-*` 前缀，再统一 mv 到终态，比边移边改名安全；最后一定要 `ls` 确认 `tmp-*` 清空。

## 校验清单

1. 每个 skill 目录名与 `SKILL.md` 的 `name` 完全一致。
2. 悬空引用检查：扫描全仓提取所有技能名，逐个确认目录存在。先排除历史任务文档和旧名对照链（刻意保留），再修剩下的。
3. 阶段链路闭合：阶段 `00` 的派发表能覆盖全部下游 skill；每个 skill 能指到上下游。
4. 职责边界成文：设计 vs 执行、写 vs 读、生成 vs 消费这类容易越界的线，要写进设计文档。
5. `make check` 通过：它会校验 skill 目录名与 `name` 一致、必需文件齐全、md 相对链接不失效。

## 产出

重构方案本身落 `task/YYMMDD_{主题}/README.md`，含背景、目标、阶段定义、编号表、职责边界、执行清单、校验结果。这份文档是下次重构的模板。
