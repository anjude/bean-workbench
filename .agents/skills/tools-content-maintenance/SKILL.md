# 鹅懂个啥内容维护

用户要求新建、编辑、调整、预览或维护鹅懂个啥的测试题目、测试结果、副本故事、场景或相关图片时使用。先读 `business-repo/uni-gknow/docs/README.md` 和 `docs/content/README.md`，再根据涉及的测试或副本读取对应任务的最新方案、配置和状态：测试见 `task/dev-flow/QB84_gknow-configurable-assessment/`，副本配置化见 `task/dev-flow/QB82_gknow-story-config/`；日常内容维护任务见 `task/daily/QBF1_gknow-content-maintenance/`。实际接口、配置格式、环境与上线状态以代码、契约和最新记录为准，未实现的副本接口不得当作已可调用。

## 内容与本地备份

- 测试与副本各用 `business-repo/uni-gknow/docs/content/assessments/{test_key}/`、`docs/content/stories/{story_key}/`；具体结构见项目 `docs/content/README.md`。测试题目、结果、配置 JSON 及相关素材，副本剧本、场景、配置 JSON 及相关素材都要保存在对应目录。尊重现有格式，副本未配置化时保存当前实际格式并记录来源，不虚构 JSON。
- 内容图片保留来源原图和实际使用的处理版本；生成或处理前先保存原文件，上传后本地文件继续保留，不能只留远端 URL。记录用途、来源、使用版本与远端 URL；上传失败也保留本地文件。若仅有远端 URL，先按合法可用来源取得原图或标注缺失，不伪称已备份。
- 新增或替换测试、副本的内容图片（包括封面、题面、结果和场景背景）时，统一调用 `tools-image-upload` 上传处理后的图片，并在相应配置中使用返回的 HTTPS URL；原图和实际上传版本仍保存在项目 `docs/content/`。上传前核对目标环境、账号与支持格式，目标端实际读取和分享/海报用途分别核验。上传失败时保留本地文件并报告，不编造地址。已有包内素材在相关内容维护或迁移时按此规则处理，不因建立规则自动批量改写已发布内容。
- 副本运行时的背景和内容图片只能通过配置引用 HTTPS 图片，不使用本地打包图片，也不要在播放器代码中写死副本专属场景。未配置图片时允许显示通用渐变；`docs/` 中的原图与压缩文件作为素材备份。
- 项目 Git 跟踪可版本管理的内容和素材；修改前确认已有文件、工作区改动和可恢复版本，不覆盖他人改动。更新本地内容时保留变更前的可恢复副本或已提交版本，记录配置版本与环境；不要把未提交的唯一副本当作备份。远端当前内容与本地文件不一致时先查明来源和版本，避免覆盖较新的内容。
- 历史快照见 `docs/content/` 下的 `legacy-config` 和 `legacy-source`；它们只是迁入时的本地副本，不能未经比对当作线上最新版本。后续维护时将确认的当前内容与素材整理到对应 key 目录，并保持来源记录。

## 按用户要求维护

1. 明确要修改的测试或副本、内容范围及目标环境；按用户要求撰写或调整，标题、叙事、题目、选项及结果的取舍由用户决定。需事实核验时保留来源；未经确认不要把草稿称为定稿。
2. 先在项目 `docs/content/` 保存或更新内容与素材，再按当前能力生成配置；维护时核对测试题目、计分与结果，或副本场景、跳转、结尾和资源；不为副本增加运行时校验框架。业务规则和模板变化属于开发需求，调用 `dev-flow`，不得自行改变已确认系统行为。
3. 生成或处理测试、副本图片时，按 [图片生成与压缩规范](references/image-spec.md) 选择画布、安全区与目标格式；保留原图，优先使用 uTools 缩放、转换和压缩，检查实际尺寸、体积及画质后，再调用 `tools-image-upload` 上传最终使用文件并将 HTTPS URL 写入配置。记录环境与目标端访问情况。
4. 按用户授权在目标环境保存配置并读取核对；预览和发布使用已有正式接口与真实小程序。先确认后端记录的版本、发布状态以及更新已发布内容是否立即生效；避免覆盖其他修改。test 保存、线上更新和公开发布分别记录实际结果，授权范围不清时先完成本地内容及预览准备，再向用户说明具体动作。
5. 维护结束更新任务 README 或 process，记录内容文件、素材、配置版本、环境、预览与发布状态；用户验收与服务端回读分别记录，不把本地文件或构建通过当作线上发布成功。
