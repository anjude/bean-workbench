# 会话续接：自动与手动入口

## 触发条件

- 自动：每次主会话模型请求成功后，以该次输入 token 除以会话记录中的模型上下文窗口。达到或超过 90% 时，后台从该会话第一轮结束位置分叉，旧会话继续回答。只使用当次输入量，不使用累计用量；请求失败、子代理请求或用量和窗口缺失时跳过。
- 手动：用户明确说「切新会话」「换个新会话继续」或要求创建续接会话时，立即执行下方手动流程。
- 每个旧会话共用一份续接状态；自动与手动重复触发时复用已经创建的新会话，避免重复分叉。新会话以自己的 ID 独立计算触发状态。
- 首轮尚未结束时，后台只等待首轮结束；已有结束的首轮时立即分叉，不等旧会话当前轮结束。

## 来源会话与注入内容

新会话的启动消息只写 `来源会话 ID：{旧会话 ID}`。不在启动消息里要求读取 handoff，不复制近期请求、答复、进展摘要、工作目录或续接规则。脚本不代写 handoff；写入或更新 handoff 时按模板记录来源会话 ID，供需要时定位任务。

新会话保留旧会话第一轮，工作目录作为分叉运行参数沿用，Git 分支沿用；旧会话保留。续接上下文优先从来源会话的实际对话中读取；handoff 只作为需要补充任务状态时的内部索引，不要向用户播报读取过程或重复任务概况。

## 新会话接手规则

收到仅含来源会话 ID 的续接消息后：

1. 读取本规则；从运行环境 `CODEX_THREAD_ID` 确认自己的新会话 ID，必须与消息里的来源 ID 不同。不要把旧会话 ID 当成置顶目标。
2. 使用应用工具 `move_thread_to_sidebar_section` 将**新会话**放入 `sectionId="pinned"`，再用 `list_threads` 核对它已在 `pinnedThreads`。工具不可用或失败时报告具体情况，不把创建成功当成置顶成功；不直接写桌面应用的内部数据。
3. 使用 `navigate_to_codex_page` 打开新会话。旧会话继续运行，不归档、不取消旧会话置顶、不停止旧轮。
4. 读取来源会话的实际对话，识别最近一条尚未完成的用户目标及已完成动作；不要只根据标题、摘要或 handoff 猜测。仅在对话不足以恢复任务状态时，按来源 ID 查找匹配 handoff，并按需读取其索引文件。无法确认来源会话或任务时，简短说明具体缺口并等待，不猜测。
5. 保留脚本已经设置的新会话名，不因自动任务绑定再次覆盖它。
6. 若任务正式记录已有用户对续接会话与特定定时任务迁移的明确授权，读取记录后核对原始字段与旧绑定，用应用自动化工具只迁移已授权、仍绑定老会话的 ID，并核验。已经绑定新会话则跳过；绑定第三个会话或更新失败时不覆盖、不宣布成功。不得直接写自动化配置文件，不迁移未授权任务。
7. 除非用户询问，不讲解续接流程、不汇报 handoff/置顶等后台步骤，也不重复整段任务状态。若来源对话中有未完成且无需澄清的明确请求，直接继续；若来源会话已完成当前动作并在等用户决定，简短表示已接上并等待下一条输入。不要自行重做日报、交易或扩大任务。

### 状态核验与报告

- 先读取来源会话对话；只有任务定位或近期状态不足时，才在各任务 `handoff/` 中按来源 ID 搜索「来源会话 ID」，随后重新枚举目标任务目录。不要只凭标题或任务主题猜上下文。
- 先用 `list_threads` 检查新会话当前是否已在 `pinnedThreads`。已经置顶就保留现状；只有确认不在置顶列表时才调用移动操作。以列表中的新会话 ID 和 `pinnedIndex` 作为置顶依据。
- 用 `navigate_to_codex_page` 打开新会话，并依据工具返回判断本次导航是否成功。不要把脚本已创建会话、会话处于 active，或工具调用失败，单独当成置顶/打开状态的证据。
- 必须区分「已完成」「已确认未完成」和「无法核实」。工具未加载、不可调用或调用失败，只能说明本轮无法执行或核验，不能据此声称操作没做。若后台动作状态与用户当前目标相关或用户询问，再用实际工具证据简短说明；否则不主动播报这些实现细节。

## 手动切新会话

在旧会话中收到明确切换要求时：

1. 更新当前任务 handoff。
2. 执行 `python3 script/codex-hooks/continue-session.py --manual`；从工作台外调用时使用该脚本的绝对路径。默认从 `CODEX_THREAD_ID` 取旧会话 ID，也可显式使用 `--session-id`；工作目录默认当前目录，可用 `--cwd` 指定。
3. 若返回 `pending`，用 `--status` 查询相同旧 ID 的状态，给后台创建留出时间；首轮仍在运行时让当前轮正常结束，后台会继续处理。不要因暂时未返回 ID 而另行分叉。
4. 返回 `ready` 后使用 `forked_thread_id` 核对新会话已置顶，并打开它；启动消息已由脚本发送，不重复发消息。尚未置顶时可直接调用上述应用工具完成置顶和核验。
5. 返回 `failed` 或 `needs_review` 时检查状态和已有子会话。特别是续接消息提交结果未知时，先读已有新会话核对，不直接重试 `turn/start`。

## 命名、状态与故障

- 命名固定为三个语义段：`任务名-短阶段摘要-两位序号`，例如 `261009_gknow-daily-海报暗色排查-02`。第一段始终是任务目录名；第二段只概括当前续接主题；第三段只表示相同前缀的续接序号。禁止把旧标题整体当任务名继续追加，也禁止重复追加「续接-序号」。任务名属于 `YYMMDD_slug` 时必须保留日期后的下划线；若 app-server 返回的旧标题省略了分隔符，脚本应按工作目录下 `task/dev-flow/` 或 `task/daily/` 的实际目录名还原第一段，再生成新标题。
- 状态与日志位于 `~/.codex/state/session-continuation/`，按旧会话 ID 隔离；本机 hook 配置在 `~/.codex/hooks.json`，注册 `PostModelRequest`。窗口来自 hook 提供的本机会话 transcript 中最近一条有效 `token_count`，该格式并非稳定接口，缺失或变化时跳过并等待后续事件。单次请求可能跨过阈值或先发生压缩，阈值触发不能保证在压缩前完成。
- 连接优先使用已有共享 app-server；共享控制套接字不存在时，启动独立 stdio app-server，沿用本机配置和账户，待新会话接手轮结束后关闭，不安装或重启常驻服务。
- 后台失败不阻断旧会话。尚未创建子会话或仅改名失败时，下次触发可继续处理；消息提交结果未知则标记待核，避免重复注入。
- `script/codex-hooks/fork-before-third-compact.py` 仅为已加载旧路径的会话保留兼容入口，转调新脚本；不再执行第三次压缩阻断逻辑。
- 配置已写入不等于桌面端真实事件链路已验收；如应用要求重新审阅 hook，在 `/hooks` 中审阅并信任后才会执行。
