## 复盘（仅在有用户反馈或规则沉淀时写）

有反馈或规则沉淀时，生成或更新 `06_复盘.md`，保持简短：

- 记录本次生产中可复用的结构
- 记录用户反馈
- 记录是否触发自进化；如果触发，写明更新了哪些文件和原因
- 如果反馈暴露出规则盲区，立即修改 content-playbook / skill 或 references，不要只改当前稿
- 把数据表现（曝光/点赞/收藏/评论/涨粉）填进该篇 `manifest.yaml` 的 `metrics`；如有新决策追加 `decisions`

## 自进化判断

每次创作、修改、发布检查、用户反馈后，都要主动判断：这次问题是当前稿的一次性问题，还是可复用规则缺口。

必须主动优化规则的情况：

- 用户明确指出某种写法不要再出现。
- 同类问题在不同稿件中重复出现。
- 发布检查发现某条禁用写法没有被现有清单覆盖。
- 当前 skill、memory、references 之间规则冲突或表达含糊。
- 生成内容时临时想出一条有效判断标准，且以后明显能复用。

不需要更新规则的情况：

- 只是当前选题的事实修正、标题取舍、局部措辞偏好。
- 用户只要求本篇换角度，不代表长期偏好变化。
- 修改会让规则过窄，影响其他类型内容正常创作。

主动优化顺序：

1. 先改当前稿，保证用户眼前问题解决。
2. 再判断规则应落在哪里：
   - 长期账号偏好、用户稳定反馈：更新 `business-repo/beannote/docs/content-playbook.md`
   - 本 skill 的流程动作、交付标准、自进化机制：更新 `SKILL.md`
   - 具体写作禁令、句式禁区、文风判断：更新 `references/创作准则.md`
   - 可验证的交付检查项：更新 `references/正文质检清单.md`
   - 模板结构或固定栏目：更新使用方 skill 的 `references/`
3. 最后更新当前主题 `06_复盘.md`，记录本次反馈和规则沉淀。

写入规则时要克制：

- 写成可执行判断，不写空泛口号。
- 附 1-3 个禁用例子或改法，方便下次检查。
- 不把一次性偏好升级成全局规则。
- 不重复写多处；如必须多处同步，分清 memory、skill、reference 的职责。

## 复盘结构

按 `references/复盘模板.md` 逐项填写，重点：

- 内容分析：核心观点是否鲜明、结构是否符合文风规范、是否有人设感有态度、是否出现禁用符号
- 读者收获感评分：读得下去 / 有收获感 / 被尊重，用 ⭐ 三星制，不打分数不写百分比（**不评传播量，不评"教会了多少"、不评行为改变，见下**）
- 做得好的地方：具体列举，不泛泛而谈
- 可以改进的地方：定位到具体段落或表达方式
- 可复用经验：提炼能迁移到未来文章的原则或句式
- 下次注意：转化为可执行动作

改进建议必须具体，指向段落或表达方式，避免"整体不错"这类泛泛评价。

**复盘不评传播量**：不设"停 / 点 / 留 / 传"这类流量维度，不给阅读量、点赞、转发定目标。发布后数据只作为"这篇有没有被读懂"的旁证记录，不作为好坏判据——把读者当目的，不当流量。
