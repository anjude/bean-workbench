# 写作风格与公共规则


本文件由 `bn-tools-edit-flow` 维护，供起草、改稿和内容检查按需读取。公共模块见 [文章公共模块](article-modules.md)，排版由 `bn-tools-format-flow` 执行。

## 用户口述改写规则

- 用户提供口述、语音转写或口述要点并要求形成文章时，口述内容就是本篇的观点与风格基准。优先保留用户的第一人称、语气、态度、判断、表达习惯和材料顺序；主要工作是理顺语句、段落和必要的事实衔接。
- 不擅自把文章改成反驳用户、纠正用户、两边平衡或替用户收束观点；不因个人判断删弱用户明确表达的立场、情绪和结论。不要把口述中的直接判断改成“似乎”“好像”等未经用户要求的弱化说法。
- 除非用户要求核查、反驳或改换角度，事实核查只用于避免捏造和帮助表述准确，不接管内容取舍。发现事实疑点、传闻或证据边界时，保留用户要表达的方向，并把核查结果作为稿外编辑备注或来源记录；确有必要时在稿内仅做准确归因（如“媒体报道”“目前仍是指控”），不借机改写成相反观点。
- 用户对某一篇稿的语气、判断或修改意见优先于通用风格建议；用户指出写偏后，直接按其口述重写，不以解释或辩护替代修改。

## 正文里的不确定信息

- 分析和事实判断以现有证据及用户明确给出的前提为依据；可以在其范围内作合理推论，先说当前能确认的结论。用必要的来源或条件限定推论，不把推论写成已核实事实。只指出会实质影响判断的证据缺口，不堆列无关假设；若关键前提无法从上下文合理确定，先向用户求证。用户明确表达的个人观点仍按其原意整理，不擅自弱化；但不要把观点包装成已经证实的客观事实。
- 正文不要插入像法律声明或免责声明的提醒句，例如连续强调「只是指控」「尚无结论」「请等待调查」来打断叙述。正式免责声明和风险提示统一放在单独的 `置顶留言.md`。
- 正文禁止出现免责声明及明显变体，包括正文图片里的声明文字，以及「不代表未来收益」「不构成投资建议」「仅供参考」「不能保证」等自我免责或重复提醒。已经交代来源和估算假设后，不再追加这类句子；把相关原文、来源、计算条件直接写清，正式风险说明放在置顶留言。若风险本身是论述内容，用具体事实和条件说明其影响，不写成免责声明。
- 事实尚未定论时，仍要准确表达，但把边界自然写进叙事和观点里：交代消息来自哪类报道、事情目前走到哪一步，再顺着主题继续讲。可以用市场反应、后续调查、当事方回应等与文章主题有关的内容承接悬念；不要为了戏剧效果把股价、传闻或任何单一信号写成事实证明。
- 准确归因不等于免责声明。避免把必要归因扩写成一段自我免责或对读者训诫；保留理解事件必需的来源和状态信息即可。

## 已确认的表达方向

- 口语化，像和朋友把一件事聊清楚，使用具体、日常的表达。公众号默认开头自我介绍为「哈喽，这里是豆小匠的笔记。」；可根据文章主题自然微调，规则见 [文章公共模块](article-modules.md)。
- 用第一人称写。可以从「一直在想……最近看了……给大家分享一下」这类由头进入，像聊天一样把话说完，不用书面报告的腔调。
- 需要说明数量关系时，用清楚的算账帮助理解，不拿数字装饰观点。先算账是当前投资文章可沿用的切入方式，不强制所有文章都这样开头。
- 正文只写对读者有用的信息，直接进入主题；不加入免责声明、空泛铺垫或重复提醒。风险与免责说明集中写在单独的置顶留言里。
- 正文只保留读者理解论述所需的来源说明和必要归因；原文链接、完整出处、参考资料或延伸阅读等对正文论述没有直接帮助的内容，统一放入置顶留言，不在正文堆放链接和资料信息。正文确有必要提及来源时，简洁说明一次即可。
- 分享不以篇幅长为目标。在内容表达清楚、因果和必要条件交代完整的前提下，优先用更凝练的表达；删掉重复解释、空转铺垫和不能增加理解的例子，不为显得完整而扩写。
- 根据内容组织结构和版面：分段表达清楚；存在不同层次时设置标题或小标题；并列内容、步骤和比较项可分点呈现；关键结论、数据或条件适度加粗；适合视觉化的信息可配图、表格或示意图。结构化表达是为了让读者更容易理解和扫读，不机械套模板、不密集强调，也不为配图而配图；必要的推理过程仍要在正文讲清楚。
- 保留分析中的分寸，用来源、条件和准确措辞表达不确定性，不把假设写成确定结果；不靠免责声明式句子重复强调，不用「熬到某一年就必然爆发」等说法推动读者采取行动。
- 分段、编号、加粗按内容需要使用；不强制四段结构、固定金句、名人引语或行动号召。
- 禁止「不是 A，而是 B」及同类变体，包括「不是 A，是 B」「不取决于 A，而取决于 B」「A 倒是其次」「说是 A，其实是 B」「A 帮不上忙，只有 B」。要表达取舍时直接写结论，或把两句并列写，不先否定再肯定。
- 不替用户加评论，尤其不写暗示读者没钱、没耐心、拿不住的句子。这类判断容易被读成嘲讽；正文只写用户给的内容和必要的事实。

## 让读者跟得上

- 开头尽早让读者知道文章在谈什么、为什么值得看；标题或开头可以先给结论，也可以用场景或问题引入，由本篇内容决定。
- 一句话尽量只推进一个判断或动作。写清楚是谁做了什么、发生了什么变化；少把动作压成连续的抽象名词，也不把几个因果步骤塞进一个长句。
- 让段落之间的关系看得出来。需要时明确写出因为、所以、但是、如果、随后等连接关系，不为了显得简洁而省掉关键推理步骤。
- 抽象概念先配上具体情境或例子，确实能帮助理解时再命名；不为追求“接地气”强加故事、比喻或口语词。
- 每段聚焦一个主要意思。保留能帮助读者理解事实、条件和结论的解释；优先删重复和空转，不删必要的说明。
- 交稿前从读者角度顺读一遍：只看标题和段首，能否大致说出文章在讲什么；逐段读时，是否知道这段与上一段是什么关系。读不顺先重排内容，再改句子。

这些检查帮助表达清楚，不规定文章必须先结论、使用固定段落结构或写成口语；标题、观点、结构和留删仍由用户决定。

## 改稿时的通用检查

把以下内容作为改稿时的判断方法，按文章实际情况取用；它们不是每篇文章都要逐项完成的清单，也不规定文章结构：

- 先看原稿或用户材料里最重要的信息和表达节奏，尽量保留有用的部分，不为了“像公众号文章”而重搭骨架。
- 读者为什么会关心这件事，可以在开头用一句话点明；只有确实能帮助读者进入主题时才加，不强行制造收益承诺、悬念或共鸣。
- 检查有没有重复解释、空泛铺垫和与主题无关的内容；删减后仍要让关键事实、条件和逻辑关系说得明白。
- 新增解释要能帮助理解，并与已有事实和用户观点一致；不为扩写而扩写，也不把推测补成结论。
- 结构、篇幅、语气和收尾都根据本篇材料与用户要求决定。步骤、问答、叙述等形式均可使用，不设默认模板。

## 免责声明模块

免责声明统一放在置顶留言，不放进文章正文。写作和排版时将正文稿与置顶留言作为两个独立交付物，避免把免责声明或客套铺垫混进正文。模块规则和题材模板见 [文章公共模块](article-modules.md)，起草或检查时读取。理解论证必需的事实、条件和计算口径仍放在正文对应位置，完整核算依据放主题 source/。

## 使用与规则更新

1. 起草、改稿前读取本文件，按当前用户要求应用相关规则；仅讨论主题时，不强制生成文章模块。
2. 本轮明确要求优先于这里的默认约定。某一篇的临时调整只记在该主题，不自动扩成全局规则。
3. 用户说「以后统一」「以后都这样」或明确要求修改风格规范时，更新本文件或文章公共模块；其他 skill 只保留引用入口，避免多处维护同一套细则。
4. 新规则要有用户指令或明确反馈依据。Agent 自己提出的建议、待确认草稿中的写法，不自动视为已经认可的风格。
5. 用户修订或撤销旧规则时直接更新有效规则，变化依据留在任务 process/；不把每轮反馈累积成越来越长的写作流程。

## 当前适用范围

用于 beannote 的公众号内容，不修改工作台技术文档的写作方式。暂不预设账号人设、字数、标题模板或具体产品的固定推荐；需要时按用户后续确认补充。
