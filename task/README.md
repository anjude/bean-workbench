# 任务管理

`task/` 记录工作台建设任务、热任务与上下文范围。本文件是任务管理约定，操作细则见各任务目录的 README 与 `.agents/skills/wb-handoff`。

## 目录职责

- `task/registry.md`：热任务、冷任务、任务目录和资源范围索引。
- `task/daily/`：长期日常任务的常驻上下文；事项可持续记录、直接开发，或转入 / 衍生为 `dev-flow` 项目。
- `task/workbench/`：工作台 / 技能 / 平台类任务。
- `task/dev-flow/`：业务仓开发 / 接入类任务。
- `task/beannote`：豆小匠内容与工具代码子模块；其中 `topics/` 的选题目录是内容工作单元，不按工作台任务目录管理。
- `task/YYMMDD_slug/`：单个工作台任务目录；`README.md` 为任务目标、范围、边界、状态入口。

## 长期日常任务

`task/daily/` 用于持续维护的产品、项目或个人工作事项，不要求每次都建立独立开发项目。每个长期事项使用稳定 slug 目录（`task/daily/{slug}/`），以 README 维护职责、当前状态、待办和关联任务；按需添加 `plans/`、`process/`、`handoff/`。

- 没有代码的跟进、研究、运营或维护直接记在 daily 任务中。
- 小型、连续的代码改动可以直接在 daily 任务上下文中按需走 `dev-flow` 的需求、设计、实现和交付环节；过程记录保留在 daily 目录。
- 目标独立、范围较大或需要单独方案/验收/交付时，从 daily 任务衍生一个 `task/dev-flow/YYMMDD_{主题}/`，在双方 README 中互相链接；daily 继续作为长期索引，不复制专项过程。
- 现有事项整体转为一次性开发项目时，完整迁移任务目录及其记录到 `task/dev-flow/`，并更新登记和所有路径引用。
- 仅因涉及代码不自动迁移到 `dev-flow`；有明确项目边界时由用户意图和任务范围决定。

## 任务命名

`YYMMDD_slug/` 目录格式；`slug` 用短英文或拼音，保持可搜索。

beannote 的发布工具、平台适配等开发任务仍使用 `task/dev-flow/YYMMDD_slug/`，在任务文档中指向 `task/beannote` 的代码位置。新增文章或笔记主题直接进入 `task/beannote/topics/`，不登记为开发任务；新建或继续选题时按选题目录名绑定并自动改当前会话名，单会话只自动绑定一次。

## 任务目录建议

- `README.md`：任务目标、范围、边界、状态。
- `handoff/`：会话交接快照，按时间戳命名，最后一份最新，高层一屏可读。
- `process/`：阶段过程记录，一个阶段一份 `{阶段号}-{环节名}.md`，记做了什么、结论、被推翻的判断。
- `review.md`：完成后复盘，按需创建。

`handoff` 是「我从哪接着干」，`process` 是「这件事怎么被想清楚的」；handoff 指向 process 文件，不复制过程内容。

## 热任务规则

热任务加速路由到最近上下文；任务完成或长期不活跃后，移到冷任务。

## 新任务合并规则

新建任务目录前先检查最近几个任务目录与 `task/registry.md`，判断是否复用。用户明确提出新建任务目录即视为已确认，不要重复询问；只有用户未明确表达创建意图，或目录归属与范围无法合理判断时才询问：

1. 同业务线 / 同流程 / 同问题链，优先合并到已有任务目录。
2. 原任务的补充、修补、验证、零碎收口，继续共用原上下文。
3. 仅当目标、边界或沉淀对象明显不同，才新建目录。
4. 合并后在 README 说明是延续任务，避免再拆。

## 子仓接入任务

接入新业务子仓时，建或更新对应任务目录，记录：子仓名称与仓位、需同步的 skill、需更新的知识库与路由提示、是否新增工作流或检查脚本、验证结果与遗留风险。保证「加子仓」不是只改 `.gitmodules`，而是完成工作台级整体收口。

## 长期日常任务的文档边界

日常任务 README 只维护职责、当前状态、待办和索引；详细方案按主题放入 `plans/`，阶段过程与交接仍各归 `process/`、`handoff/`。产品定位、角色与品牌等长期事实进入所属业务仓 `docs/`。有独立目标和验收标准的项目单独建档，工程与过程一起迁移。重命名或拆分时同步更新登记、路由、知识库、业务仓指南和所有路径引用，不因引用存在而保留失准的目录名。
