# 长期日常任务

`task/daily/` 保存需要长期跟进的产品、项目或个人工作事项。它与一次性专项任务并列，允许事项在不同回合涉及研究、运营、维护或代码开发。

## 使用方式

1. 新增事项前查本目录与 `task/registry.md`，能沿用已有上下文就继续沿用。
2. 新事项建立稳定 slug 子目录：`task/daily/{slug}/README.md`，并在登记中加入热任务路由。不要按日期重复新建长期任务。
3. README 维护目标、职责范围、当前状态、待办和专项任务链接；按需添加 `plans/`、`process/`、`handoff/`。过程记录按 `wb-handoff` 的格式维护。
4. 无代码事项直接在 daily 上下文推进。持续的小型开发也可以留在这里，按 `dev-flow` 的需求沟通、轻量设计、实现迭代和交付要求完成，并将过程记录写在 daily 任务目录。
5. 当某件事有独立目标、验收标准或需要单独交付时，衍生 `task/dev-flow/YYMMDD_{主题}/` 专项任务；专项 README 与 daily README 双向链接，详细方案和过程留在专项任务。daily 保留长期索引与待办。
6. 如果整个 daily 事项已变成边界清晰的一次性项目，可以将任务目录整体迁入 `task/dev-flow/`，同步更新 registry、路由和所有引用；不要只迁代码而丢失过程与交接记录。

## 任务目录建议

```text
task/daily/{slug}/
├── README.md       # 长期职责、状态、待办与专项任务索引
├── plans/          # 按主题记录的方案，仅需要时创建
├── process/        # 阶段过程记录，仅需要时创建
└── handoff/        # 跨会话交接，仅需要时创建
```

日常任务 README 模板：

```markdown
# {事项名称}

## 目标
长期希望持续推进的结果。

## 范围
- 长期负责的事项与资源。

## 当前状态
当前进展和待办。

## 专项任务
- 暂无
```

开发流程入口仍是 `.agents/skills/dev-flow/SKILL.md`。使用 daily 目录不改变开发阶段要求，只是让连续小改动共用长期上下文；独立专项的方案、验收与交付在其 dev-flow 目录收口。
