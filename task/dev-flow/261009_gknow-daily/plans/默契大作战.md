# 默契大作战

- 状态：前后端代码已接入，真实服务未部署、真实目标端链路未验收；等待用户先部署。
- 定位：两人同时在线作答，双方确认后一起揭晓，让差异成为聊天话题。

## 已讨论的方向

- 发起人创建房间，选择一个或多个分类，也可选择全部分类；选择 5、10、15 或 20 题（档位为建议），邀请朋友加入。
- 情感、生活、友情、脑洞、旅行、职场、美食等分类；题型包含 0～10 分打分和四选一选词。本局随机抽题、不重复。
- 双方确认前互不展示答案；确认后同时揭晓，双方准备后进入下一题，结束展示相同选择和分差等真实结果。
- 扩充题库需关注具体情境、自然选择和可聊性；用户认可第一批样题方向，题目继续迭代，不用数量替代内容质量。

## 同步设计待落实

现有 `common/fe_redis/get`、`set`、`del` 只能读取和覆盖整值，并发读改写可能丢失答案。考虑增加基于版本的原子条件更新，冲突后重新读取、校验并重试；需要进一步设计房间创建、参与者身份和权限、双人占位、答案保密、重复请求、断线恢复、过期及推进状态。通用 CAS 本身不保证这些业务规则，不能将客户端检查当作服务端保证。

客户端定时拉取或其他同步方式、轮询频率、房间有效期及异常处理待结合现有后端和小程序约束确定。接口涉及 `backend-superone`、`frontend-contracts` 和 `uni-gknow`，需先形成具体契约和验收设计。

## 样题

- 情感／打分：他是满分男，但每次吵架都要消失一天，等自己想通了才回来。你给几分？
- 情感／打分：她是满分女，但约会吃什么、去哪儿，永远回答“都行”。你给几分？
- 生活／打分：室友很爱干净，但你刚放下的杯子，他立刻拿去洗了。这个室友打几分？
- 友情／选词：朋友发来“在吗，有件事想问你”，第一反应是？紧张／好奇／警惕／先回在。
- 脑洞／选词：突然有一项超能力，先试哪个？瞬间移动／听懂动物说话／时间暂停／一觉恢复体力。
- 旅行／选词：到陌生城市先做什么？找吃的／去景点／随便逛／回酒店躺着。
- 美食／选词：两人点外卖只能加一道菜，选什么？炸鸡／青菜／甜点／汤。

首期题库按分类持续扩充；题目由双方各自独立作答，再比较选择，不依赖一方掌握另一方的私人经历。当前数量与抽题规则见下方更新记录。

## 2026-10-30 近实时后端方向

用户反馈切题太慢，要求开始后端接口。当前客户端每秒轮询、一次刷新多次 Redis 读写；揭晓后另有 1.8 秒固定停留，均影响体感。此前同意的前端简单读改写不保证多人并发正确。

拟用一个 WebSocket 连接入口承载创建、加入、作答、同步、离开等消息；服务端持有房间状态机，Redis 原子完成成员占位、答案写入及状态推进，状态变化推送给双方。连接断开后重新鉴权并恢复快照；Redis 状态是事实来源，推送只是通知。多实例部署须使用 Redis Pub/Sub 或等价的跨实例通知，不能依赖进程内广播。先不将前端自行提交的身份或题号作为可信事实；未揭晓时只向对方发已作答状态。

单个 WebSocket 路由可承载多种动作，但不是增加一个通用原子读写 HTTP 接口就能同时获得实时通知和完整房间保障。需要共同设计消息契约、身份鉴权、房间有效期、重连、重复提交、超时和错误状态；同步前端与唯一协议仓。检查部署代理是否支持 WebSocket 升级、小程序合法域名、连接数和超时；仓库已有 gorilla/websocket 依赖，但尚未证实生产链路可用。

揭晓停留时间与网络同步分开考虑：可先用约 0.8 秒作为体验初值，双方收到揭晓后显示；对于弱网及后台恢复，需要确保双方都能看到结果再推进。实际时延受网络及部署影响，不承诺固定数值。以上为设计方向，尚未实现、验证或部署。

## 2026-10-30 通用实时房间方案（用户确认开工）

### 目标与范围

建立与玩法无关的 WebSocket 房间：服务端管理成员、可恢复的共享数据和成员私有数据、CAS 与事件转发；题目、状态结构、游戏规则由客户端确定。默契大作战首个接入。没有 SQL 数据库变更，不动已有 fe_redis 接口；旧体验版房间与新协议不互通，旧房间继续使用旧代码直至过期。

### 实施落点

- `backend-superone/app/api_service/api_service.go` 注册 WebSocket 路由，房间业务代码新增独立模块，复用 Redis 与 JWT，不依赖通用 HTTP DTO 的请求包装。
- `frontend-contracts` 增加通用房间消息类型、路径及协议说明；客户端通过 `uni-gknow/src/contracts` 子仓消费同一修订，不能在客户端复制协议。当前两者为独立 checkout，同步修订须遵守不擅自提交的约定。
- `uni-gknow/src/utils/adapt/` 封装小程序 socket，`src/composables/useTacitBattle.ts` 改用协议，页面承接连接、断线和恢复状态；保留现有页面和题库样式。
- Redis 以 appId、房间随机 ID 分区；共享状态、版本、成员和私有数据均限大小、数量和有效期；禁止读取别人的私有数据，重连按服务端鉴权身份恢复。JWT 和房间内容不得写入日志。

### 消息与一致性

单条连接携带经现有 JWT 验证的身份。动作至少包含创建、加入/恢复、共享状态 CAS、读写本人私有数据、发送房间事件、离开、心跳；每个请求有请求 ID，回应明确成功、冲突、满员、过期、无权限、数据超限和失败，事件通知带房间版本。房间成员和版本检查、状态写入与有效期采用 Redis 原子脚本；不把未经认证的 openid 或客户端提供的身份视为可信。成员私有数据默认只给本人；通用事件按成员权限转发，不把它当持久化状态。状态变更通过 Redis Pub/Sub 跨实例通知，断线重连先订阅再取快照，以版本去重并弥补订阅窗口，丢通知时应有重同步手段。

自动揭晓时每个玩家各自提交答案到私有数据，公开自己已作答状态；双方都已作答时客户端按通用协议显式公布自己答案，所有人看见后各自等待约 0.8 秒，自动写入已展示状态，协调一方 CAS 推进题号。用户已接受通用服务不执行游戏业务规则，故无法提供严格防作弊或强制揭晓条件。掉线时显示等待并允许恢复；连接失败提供重试；房间过期、满员和权限失败提供明确提示。不得用本地计时替代共享状态协调。

### 验收

本地 Redis 和多个后端实例验证：房间创建与容量、身份隔离、私有数据不泄露、并发 CAS 至多一个成功、重复消息、发布/订阅跨实例、断线恢复与事件丢失恢复、过期和限制、单人退出及网络故障；前端双账号覆盖创建邀请、双方盲答、揭晓、自动推进、最终汇总与断线恢复；运行后端针对性测试、契约与前端类型检查、微信构建。测试环境上线、线上 Nginx 握手与真实微信双账号验收需对应环境可用；不得把本地检查当线上通过。
