# 鹅眼中的我和我眼中的鹅 · 首版方案

- 更新：2026-10-29
- 状态：2026-10-29 已完成多人填写修订，填写人独立key、人数图鉴、填写记录列表及逐条回看；本地验证通过，后端不改，待微信端多账号验收，未发布。

## 已确认的取舍

- 直接复用现有fe_redis/get、set、del接口，不增加业务API，不建数据库表，不做原子抢占，不以并发安全作为本期目标。
- key采用openid加功能key，同一用户本玩法只有一个待完成分享槽位。
- 取消占用：朋友均可直接填写；提交前读取状态，尚未完成则写入自己的结果，已完成则提示“已有朋友完成这次对照了”。
- 本机维护可扩展的任务队列，后续可加入其他功能任务。按用户身份区分；换设备或清本机缓存后不恢复任务队列，符合当前产品本地存储方式。
- 拉取结果并保存图鉴成功后删除Redis，再移除本机任务；重复取回直接覆盖该玩法结果即可，不强调计数。
- 图鉴保留最近一次处理的结果，不按完成时间做排序。
- 读取成功但key不存在时显示“已过期或不存在”；网络失败属于请求失败，保留待办以便重试，不能当作不存在。

## 主流程

1. A完成自评，写入Redis并登记本机任务队列，分享携带对应key和本轮taskId。
2. B、C均可读取并直接开始填写，填写期间不写Redis状态，不阻挡其他朋友。
3. B提交前重读，确认本轮taskId一致且status为waiting，再写completed、respondentId和答卷。C稍后提交若已completed则提示“已有朋友完成这次对照了”；若respondentId为自己则按已提交成功处理。请求失败保留本机答案。
4. A进入小程序或回前台，检查本机队列，读取Redis。等待中展示等待朋友；completed则保存图鉴。
5. 保存成功后del，删除成功再移除本机任务；删除失败下次重试。key不存在时移除该待办并按需要提示。

## 候选数据

key：`{openid}:{featureKey}`，featureKey使用稳定的玩法标识。

value：version、taskId、ownerId、selfAnswers、status（waiting/completed）、respondentId、friendAnswers、createdAt、expiresAt。

本机通用任务项：type、redisKey、taskId、createdAt、expiresAt。处理器按type分发，不把新玩法逻辑塞进所有任务处理分支。

## 实现时的简单约定

- 七天从首次创建计时；每次set传expireSeconds为expiresAt减当前时间的剩余秒数。剩余不足一秒视作到期，不传零值（现有接口零值会使用默认一年）。
- 不设置填写占用、填写超时或续期。多人可以同时作答，以提交时读到的已完成状态阻止后续提交。
- 同key意味着A重开测试会影响原分享。建议已有未结束任务时提示继续或重新开始；重新开始生成新taskId，旧链接不匹配时显示已失效，避免旧分享读到新题。
- 分享本轮taskId也写入本机队列，读写前核对，减少误处理旧任务；本方案接受先读后写竞争。极少数同时提交仍可能后写覆盖先写，不承诺严格“第一人获胜”，按用户指定小规模取舍实现。
- A读取自己的key进入等待或领取；A不能作为朋友填写自己的测试。
- 朋友页面在提交前不展示自评答案。现有通用接口会返回完整value，所以这只是正常界面的隐藏，不具备服务端盲答或记录级权限隔离；本轮按用户要求不增加后端能力。
- 读取不存在、接口失败分开处理；写图鉴失败不删Redis；删除失败不丢待办。

## 2026-10-29 多人填写修订（本轮执行依据，替代单人结束规则）

用户要求一人发起、多位朋友填写，每份答卷以发送人openid和填写人openid组成key；图鉴显示填写人数，详情进入游戏首页，首页增加记录入口可看所有人及逐题对照。

- 保留 `${ownerId}:goose-mirror` 发起key，存自评、taskId及respondents（填写人openid索引）；新答卷key为 `${ownerId}:${respondentId}:goose-mirror`，每人每轮一份。只靠独立答卷key无法通过现有get接口列举未知填写人，因此索引保存在发起数据中，仍不改后端。
- 各答卷保留本轮自评快照，后续重测不会改变已经归档的历史。新一轮同一人答卷覆盖对应Redis key，本机历史以taskId+respondentId去重保留。
- 提交先写个人答卷再追加发起索引；索引写失败可重试补登，重复提交本人返回已有结果。多个朋友独立作答，其他人已提交不再阻挡新朋友。
- 沿用小规模前端读改写取舍，不增加锁或后端；索引并发覆盖的极少数竞争不作为本期目标。
- 邀请与每人答卷有效期均为邀请创建起七天；领取后保留远端数据到期，让同一邀请继续收集、本人可回看。待办持续至邀请过期，不再一份领取后结束。
- 图鉴本机存多份答卷，按参与者openid统计人数；同一朋友多轮记录均可查，人数去重；列表逐条显示昵称、填写时间、对照摘要和本轮六题。
- 现有mirrorResult继续作为最近处理结果，新mirrorResults容纳累积记录；扩展保存时保留已有单份结果，避免丢弃本工作区已有图鉴内容。
- 首页状态改为发起人游戏首页，包含当前邀请/重测、填写人数、“填写记录”；无有效邀请但有本机历史时仍能查看。列表初始/空/有数据/刷新失败/记录详情状态齐全，可从详情返回记录。
- 修改data、API、mirror-tasks、useGooseAtlas、useGooseMirror、玩法页/样式及图鉴首页跳转与展示。后端、协议、六题文字不变。
- 验收：B/C都能提交且答卷不同key；A同步两人、重复同步不重复计数；朋友重复进入回看；索引失败重试；过期不影响本机历史；重测保留历史；图鉴显示人数并跳首页；列表可逐条看六题。

## 2026-10-29 单用户key与朋友结果修订

用户确认每个openid一个玩法key，B填写A后只看匹配题数，不在B的key保存这次填写。A的key保存A最新自评及朋友对照记录；每条记录保存两人当时的选项快照，七天有效。A本机图鉴继续保存历史并按朋友去重计数；B可重复填写，A的同轮同一朋友记录更新为最近一次。复用现有get/set接口，不新增后端与组合key，沿用此前用户接受的前端简单读改写。页面与数据、图鉴领取一起调整；验证多人、重复填写、快照与B的结果呈现。

## 2026-10-29 旧分享继续有效

用户要求重填后旧分享继续使用。分享仅携带发起人的key；旧分享即使携带旧taskId也不用于限制读取。朋友打开和提交时按key读取当前自评，提交时保存双方当时的答案快照。发起人重填时保留历史记录并刷新key有效期；key不存在或过期仍显示失效。内部taskId保留用于记录不同轮次和本机去重。
