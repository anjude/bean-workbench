# 鹅眼中的我和我眼中的鹅 · 首版方案

- 更新：2026-10-29
- 状态：用户确认采用轻量前端方案，后端不改；题目与页面设计尚未完成，未开始实现。

## 已确认的取舍

- 直接复用现有fe_redis/get、set、del接口，不增加业务API，不建数据库表，不做原子抢占，不以并发安全作为本期目标。
- key采用openid加功能key，同一用户本玩法只有一个待完成分享槽位。
- 取消占用：朋友均可直接填写；提交前读取状态，尚未完成则写入自己的结果，已完成则提示“已有朋友完成这次对照了”。
- 本机维护可扩展的任务队列，后续可加入其他功能任务。按用户身份区分；换设备或清本机缓存后不恢复任务队列，符合当前产品本地存储方式。
- 拉取结果并保存图鉴成功后删除Redis，再移除本机任务；重复取回直接覆盖该玩法结果即可，不强调计数。
- 图鉴保留最近一次处理的结果，不按完成时间做排序。
- 读取成功但key不存在时显示“已过期或不存在”；网络失败属于请求失败，保留待办以便重试，不能当作不存在。

## 主流程

1. A完成自评，写入Redis并登记本机任务队列，分享携带对应key和本轮taskId。
2. B、C均可读取并直接开始填写，填写期间不写Redis状态，不阻挡其他朋友。
3. B提交前重读，确认本轮taskId一致且status为waiting，再写completed、respondentId和答卷。C稍后提交若已completed则提示“已有朋友完成这次对照了”；若respondentId为自己则按已提交成功处理。请求失败保留本机答案。
4. A进入小程序或回前台，检查本机队列，读取Redis。等待中展示等待朋友；completed则保存图鉴。
5. 保存成功后del，删除成功再移除本机任务；删除失败下次重试。key不存在时移除该待办并按需要提示。

## 候选数据

key：`{openid}:{featureKey}`，featureKey使用稳定的玩法标识。

value：version、taskId、ownerId、selfAnswers、status（waiting/completed）、respondentId、friendAnswers、createdAt、expiresAt。

本机通用任务项：type、redisKey、taskId、createdAt、expiresAt。处理器按type分发，不把新玩法逻辑塞进所有任务处理分支。

## 实现时的简单约定

- 七天从首次创建计时；每次set传expireSeconds为expiresAt减当前时间的剩余秒数。剩余不足一秒视作到期，不传零值（现有接口零值会使用默认一年）。
- 不设置填写占用、填写超时或续期。多人可以同时作答，以提交时读到的已完成状态阻止后续提交。
- 同key意味着A重开测试会影响原分享。建议已有未结束任务时提示继续或重新开始；重新开始生成新taskId，旧链接不匹配时显示已失效，避免旧分享读到新题。
- 分享本轮taskId也写入本机队列，读写前核对，减少误处理旧任务；本方案接受先读后写竞争。极少数同时提交仍可能后写覆盖先写，不承诺严格“第一人获胜”，按用户指定小规模取舍实现。
- A读取自己的key进入等待或领取；A不能作为朋友填写自己的测试。
- 朋友页面在提交前不展示自评答案。现有通用接口会返回完整value，所以这只是正常界面的隐藏，不具备服务端盲答或记录级权限隔离；本轮按用户要求不增加后端能力。
- 读取不存在、接口失败分开处理；写图鉴失败不删Redis；删除失败不丢待办。
