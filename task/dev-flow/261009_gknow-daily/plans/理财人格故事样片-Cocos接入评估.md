# 理财人格故事样片：Cocos 接入评估

## 背景

用户希望用一段完整、可玩的故事测评大众的「理财人格」，故事中的选择和变化服务于测评；每种人格倾向平等，不形成投资准入或投资建议。本轮讨论的故事方向为跟随阿白经历一趟鹅湾夜航。

用户同意先做一小段样片，并询问通过 Cocos 游戏引擎实现。本方案先确定样片运行形态，避免把小游戏构建产物误当成普通小程序页面集成。

## 需求理解

做一段短故事技术样片，验证场景交互、动态分支和选择记录能否形成顺畅体验；是否使用 Cocos 取决于它能否合规地进入现有 uni-app 微信小程序。

## 目标与边界

### 本期目标

- 只做一个可完整走完的故事片段：码头准备、夜航变化、一个分支结果。
- 玩家通过场景操作和资源安排表达偏好，不出现问卷式自我评价、正确选项或人格优劣分。
- 记录少量本地行为信号，形成可回看的分支轨迹；不接后端、不收集个人资料。
- 在现有小程序中完成一个可完整走完的故事样片，观察故事节奏、分支和结果表达。

### 本期不做

- 不实现完整理财人格题库、最终结果算法或分享海报。
- 不接入金融产品、投资推荐、账户数据或服务端接口。
- 不改变小程序注册主体、服务类目或线上发布形态。
- 不把 Cocos 微信小游戏构建物直接复制进 uni-app 并假设可运行。

## 实施方案

检索适配方案后的结论：

- DCloud 文档说明，uni-app 微信小程序支持原生微信自定义组件（放在 `wxcomponents/`）；这说明可以承载平台原生组件，但文档没有说明可直接承载 Cocos Creator 游戏运行时。
- Cocos 官方 Creator 手册提供「微信小游戏」构建目标，输出包含小游戏入口和项目配置；没有找到官方的「普通微信小程序」构建目标或 uni-app 页面嵌入流程。Cocos 官方论坛对 Creator 3.8.4 的答复也明确表示不能构建普通微信小程序。
- 本次在 DCloud 插件市场与公开代码检索中，没有找到维护状态、版本兼容范围和微信小程序真机验证均明确的 Cocos Creator → uni-app mp-weixin 适配器。不能把“uni-app 能接原生自定义组件”推断成“Cocos 已可嵌入”。
- 2026-10-22 用户确认：先用现有 uni-app 做故事样片。

参考：

- [uni-app 小程序自定义组件支持](https://uniapp.dcloud.net.cn/tutorial/miniprogram-subject)
- [Cocos Creator 4.0 发布到微信小游戏](https://docs.cocos.com/creator/4.0/manual/zh/editor/publish/publish-wechatgame.html)
- [Cocos Creator 社区关于普通微信小程序构建目标的答复](https://forum.cocosengine.org/t/how-to-build-wechat-miniprogram-with-cocos-creator-3-8-4/61497)

当前有三种运行路径：

1. **现有 uni-app 小程序内实现样片**：使用 uni-app 页面/Canvas 表达场景，不使用 Cocos。可以留在现有 AppID 和导航中，直接验证故事节奏与动态分支；但不能验证 Cocos 引擎。
2. **Cocos Creator 构建独立微信小游戏**：可验证真实 Cocos 场景和微信小游戏运行时；它是小游戏工程，不是普通小程序页面，不能直接并入当前 uni-app 页面。现有产品文档记录了个人主体与当前服务方向的类目准入问题，独立小游戏还需另行核对主体、类目和发布条件。
3. **uni-app 内嵌 Cocos 运行时适配**：目前没有发现可用且维护明确的现成适配器。理论上可研究自定义组件或自建运行时桥接，但将涉及渲染上下文、触摸事件、生命周期、资源加载与分包等适配，本次不采用。

本次采用路径 1：在现有 uni-app 页面用原生 view 与 CSS 场景完成一个故事样片，以验证测评玩法，不引入 Cocos 运行时。如果后续仍要测引擎，再另建独立小游戏工程验证 Cocos 运行时。

- 新增 `src/pages/quiz/finance-personality/index.vue`、`src/composables/useFinancePersonalityStory.ts`、`src/data/financePersonalityStory.ts`，注册 `src/pages.json`；在 `src/data/projectCatalog.ts` 增加首页「趣味测试」入口。使用现有品牌头像和 CSS 绘制场景，不新增外部图像资产。
- 路径 2：创建独立 Cocos Creator 试验工程，制作同一故事片段；不接入当前小程序、不发布，待平台条件确认后再讨论产品连接方式。
- 路径 3：仅在确认适配器可在当前 uni-app/微信基础库稳定运行后，再设计自定义组件桥接；游戏状态和结果数据通过明确的消息接口回传页面。

## 验收标准

依据确认的路径验收：

- 用户可从开场完整走到片段结尾，至少有两条体验不同的路线。
- 每个选择都能改变后续场景或获得的信息；没有正确/错误、输赢或人格高低提示。
- 选择轨迹可供结果页总结；不同分支都能正常结束和重新开始。
- 如果目标是现有小程序：不得依赖 `<web-view>` 或小游戏专属 API；微信小程序构建通过，并在开发者工具真机检查启动和页面返回。
- 如果目标是独立小游戏：Cocos 工程可构建运行；不以此宣称已完成现有小程序集成。

## 推荐实施顺序

1. 先确认样片运行路径与当前个人主体/类目边界。
2. 路径确定后，使用 `dev-flow-0201-archetype-flow` 固定互动原型和状态，再用 `dev-flow-0203-page-flow` 实现；若走 Cocos 独立小游戏，补充工具链和工程目录约定。
3. 完成后按用户确认的平台目标验证；现有 uni-app 路径执行 `npm run type-check` 与 `npm run build:mp-weixin`。

## 产品原型与状态摘要

- 原型：沉浸式互动叙事。玩家在「鹅湾夜航」里自由查看物件、安排有限贝壳、遇到行程变化并临场处理；场景操作推进故事，不做逐题自我评价。
- 页面骨架：故事封面（开始）→ 码头探索/准备 → 夜航变化及分支反馈 → 灯会临时选择 → 旅程回顾/理财人格样片结果（重玩、回首页）。
- 主 CTA：开始夜航 / 登船 / 继续旅程；次 CTA：点场景物件查看线索、返回上一幕、重玩。
- 状态矩阵：首次进入显示封面；场景进行中显示可交互物件和剩余贝壳；动作处理中禁用重复点击并给出即时反馈；分支根据先前持有物和选择展示不同剧情；无剩余贝壳仍提供免费剧情路线；完成后展示「本次故事观察」结果；重玩清空内存状态；退出/重进按新旅程开始。无网络、服务端数据、权限和持久缓存状态，因为样片全本地运行且不保存个人数据。
- 结果边界：只总结本片段中观察到的偏好，不给适宜性判断、金融产品建议或风险等级。

## 本次前端原型判断

- 属于 `detail / immersive`：主任务是走完一段连续故事，而不是浏览内容列表或填问卷。
- 互动以场景里的行动和后果呈现；问题式文字只作为角色对话或环境信息，不连续展示选项题。
- 结果文案只描述这次旅程中的可观察行为，并提示样片结果不等于长期人格结论。

## 风险与回滚

- 技术风险：Cocos 微信小游戏输出和普通小程序页面属于不同目标运行时；集成不成立时不能靠复制构建目录解决。
- 平台风险：产品现有准入记录提示个人主体与当前测试/小游戏方向的类目适配仍待解决；任何小游戏形态的对外发布需另行复核。
- 工具风险：本机未检测到 Cocos Creator，若选独立小游戏路径，需具备编辑器后才能构建与预览。
- 回滚：样片只新增独立页面/工程；可通过移除临时入口和新增页面/目录撤回，不改既有功能。

## 2026-10-22 画面与叙事重做

用户反馈现有画面、动画和故事节奏不足，授权重做同一段样片。沿用 uni-app 路线和原有行为状态，呈现层改为全屏分镜叙事。

- 画面：新增统一美术风格的码头、海上、灯会三张原创场景图；保留品牌阿白头像作为说话者，不将头像悬浮拼贴为场景人物。
- 节奏：封面 → 邀约 → 收到 12 枚旅费 → 购买 4 枚来回船票 → 码头探索 → 离岸 → 风浪中的选择 → 靠岸 → 灯会选择 → 返航回顾。每个镜头只承担一个信息点，点击推进，标点停顿，文字可快进。
- 交互：码头通过画面热点进入小铺或打听航程；小铺购买物件，主场景仅保留登船主操作。选择反馈通过对白、预算变化和后续剧情呈现。
- 动效：持续缓慢镜头推进、海面光带、海上风雨、灯会漂浮光点；切换场景用遮罩和交叉淡入，购买时显示预算变化。所有动画以 transform/opacity 为主。
- 状态：封面/分镜/探索/小铺/途中选择/选择反馈/结束；打字时点击可补全文字；转场中屏蔽重复操作；预算不足保留免费路线并明确说明；本地场景图加载失败时提供重试且保持文字可读；重玩清理镜头和定时器。
- 验证：类型检查、微信构建和构建体积检查；依据业务仓约定，微信开发者工具交互由用户验收。本轮不以构建通过替代对画面和玩法的端上验收。

## 2026-10-23 用户纠正：简线条二维卡通美术

用户明确「二维动画」指美术语言：简洁线条、平面色块、二维卡通；此前理解成动画资源方案和写实分镜不准确。本轮只按美术方向重画三幕并统一 UI，沿用故事、预算与交互状态，不引入新的动画引擎。

- 界面要求：纸色底、墨色文字、少量暖色强调，按钮与对白采用清晰描边，去掉写实插画配套的暗色遮罩与电影质感。
- 资源：内置 image_gen 重绘同一三幕，新的文件使用独立命名。旧写实版本归档到工作台预览目录，不继续作为当前小程序场景资源。
