## 已确认的接口方向

- 用户确认复用现有前端命名空间 `so:fe_cache:`，暂不增加用户隔离，也不引入严格版本号来检测 A→B→A。沿用现有共享行为，前端不能指定后端其他命名空间。
- 单 key 比较并设置：传业务 key、预期旧值与新值；区分 key 不存在和空字符串，返回成功或冲突。保留原 key 的 TTL；新建、显式设置 TTL 及缺失值的接口语义与兼容方式在具体接口方案确定。现有 `get` 将不存在与空字符串都表示为空，不能仅依赖它区分两者。
- Redis 8.4 起支持 `SET ... IFEQ`；当前 Redis 6.2.6 不支持。Go 客户端新源码有 `SetIFEQ`，标为实验性；当前项目 `go-redis/v9 v9.3.0` 无该方法，最新源码要求 Go 1.26，当前项目 go.mod 使用 Go 1.24 和 toolchain 1.24.5。可考虑升级客户端或经已有 `Do` 调用 Redis 8.4 命令，需核对项目 Go/部署工具链及返回值。不存在时另用 `SET NX` 或明确模式，不把不存在与空字符串混为一谈。
- 现有实时房间代码使用 Lua 组合成员检查、版本比较、状态更新和通知；单 key `SET IFEQ` 不会自动替代这一整组语义。可评估以 Go 的 WATCH 事务重写，但需保持原子性、冲突、过期和通知语义，不因单命令支持就删除房间规则。

## 可评审的升级顺序

1. 核对 `redis` 真实运行参数、认证、配置文件、数据目录、挂载、网络与全部消费者，并评估可用内存和磁盘；不输出凭证。确认主实例持久化模式和恢复点，再制定业务写入停止窗口。
2. 在隔离的 Redis 8.10.3 测试实例中验证配置、旧版备份的恢复、现有 `go-redis` 和业务命令、过期、原子接口、Pub/Sub、连接恢复及资源占用；不得将隔离实例挂载到正在使用的生产数据卷。按用户部署规则由用户先部署目标服务后再进行真实客户端联调。
3. 约定维护窗口并明确授权后，暂停或隔离写入，制作一致性备份并验证可恢复；记录原镜像 ID、容器配置和卷、回滚步骤。使用固定版本重建主容器，保留原网络、认证、数据卷和配置，不直接改 `redis_bjq`。
4. 确认 Redis 版本、加载状态、数据、后台任务和现有服务连接；实际验证测试与生产 API、授权后再验证新命令及实时房间。若失败恢复旧镜像与升级前备份，说明回滚到旧备份可能丢失升级后写入，不能把新版本写过的数据目录直接当作旧版本可读。切换期间 Redis 及依赖服务会短暂中断。

当前只做只读核查，未创建备份、变更容器、修改配置或重启服务。以上是方案，不代表升级已获执行授权，也不代表已完成兼容性验证。
