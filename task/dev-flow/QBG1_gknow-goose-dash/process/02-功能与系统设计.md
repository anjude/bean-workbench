## 做了什么

- 根据用户关于 Three.js 的问题，明确实施技术建议为 uni-app Vue 3 原生 2D 页面、CSS 动画与 TypeScript 规则状态，不引入 Three.js。
- 将页面、玩法规则、实时房间同步和大鹅生长阶段资产职责写入 [大鹅冲刺方案](../plans/大鹅冲刺方案.md)。

## 得到的结论

- 游戏画面由普通 Vue/uni-app `view`、`image`、SCSS 组成；五条赛道和上下生命条走页面布局，大鹅作为同品种四阶段 2D PNG，移动用 CSS `transform` 与过渡动画。
- `useGooseDash.ts` 承载页面状态流程，TypeScript 规则负责预告队列、计时发放、赛道位置、事件结算与胜负；动画帧只在本地渲染，不同步每帧坐标。
- 双人状态沿用通用实时房间和 `compare_set`，共享队列、待部署鹅、双方生命、赛道单位和模拟进度；无需 Three.js、WebGL、独立游戏引擎、后端新接口或数据库表。

## 被推翻的判断

- 无。用户询问 Three.js 或其他实现方式后，按现有 uni-app 工程和 2D 赛道画面选择最小实现。

## 2026-11-16 第 7 轮：撤回拔河比喻并统一推线玩法

### 做了什么

- 用户指出拔河绳被拉动与鹅逐只越过对方基线扣分是两套不相容动作；撤回拔河包装及绳标设计。
- 统一方案为两队鹅在各自赛道方向冲刺、队伍力量求和并推动交锋线；每只鹅越过对方基线时扣对方一次分。
- 将计分示意重画为五赛道队伍合力推线与单鹅越线扣分：`../plans/diagrams/计分机制示意.png`。
- 明确操作是鹅定时提供、玩家点击赛道部署，部署后自动冲刺；不用拖拽。

### 得到的结论

- 每只鹅冲过对手基线都会单独扣对方分一次；界面显示双方总分，不显示鹅的力量、速度和扣分数值。

### 被推翻的判断

### 待核 / 没答上来

## 2026-11-16 第 8 轮：长绳与中央漩涡机制

### 做了什么

- 按用户最终玩法描述，将方案从鹅群推线修订为绳阵：新鹅跑到本队队尾加入拉绳；对方前排鹅被拉入漩涡后，我方得分。
- 重画绳阵机制图，展示基地、鹅队列、长绳标记、中央漩涡和得分结果：`../plans/diagrams/赛道绳阵机制示意.png`。

### 得到的结论

- 队伍总力量相等时标记不动；力量较强一方拉动绳子，把对方鹅带向漩涡。
- 得分在每只对方鹅被吸走时分别结算；力量、速度与单鹅得分仍是隐藏属性。
- 玩家操作仍是鹅到时后点选赛道部署，鹅自动跑至队尾并加入拉绳，不需要手动拖动绳子。

### 被推翻的判断

- 鹅群推线、鹅冲过基线扣分 → 由用户提出的长绳—队尾入队—漩涡吸鹅得分机制替代。

### 待核 / 没答上来

- 胜利目标分数、不同型号得分、绳标位移和漩涡吸入判定需配置与试玩校准。


## 2026-11-16 第 9 轮：把部署选择变成可比较的策略

### 做了什么

- 用户追问新绳阵规则下策略在哪里，以及如何得出最佳部署。
- 在方案中补充合力差、速度生效时间、预期净得分比较和集中/分散/保护前排的对抗取舍。

### 得到的结论

- 每次只获得一只待部署鹅，五条赛道构成部署选择；部署影响本队总力量、绳标趋势、双方前排被吸入风险与单鹅分值。
- 设计平衡要避免固定的全大鹅集中或永远补最弱赛道成为最优策略；用预告队列和对手布局回放检查策略支配。
- 玩家只观察鹅型、队列、绳标和发力状态；预期净得分公式只作为设计/平衡工具，不显示隐藏数值。

### 被推翻的判断

- 只凭“小鹅分散、大鹅集中”就能形成策略 → 新绳阵中小鹅也是高价值目标，策略要同时计算对方吸鹅收益与己方失鹅风险。

### 待核 / 没答上来

- 实际力量/速度/得分曲线与最佳部署需要通过确定性模拟和真实试玩校准；在数值范围确定前不能宣称某个型号或分配方式恒为最佳。
