## 背景

beannote 已有主题目录、编辑/排版/发布工具和 Chrome 源信息采集插件，但能力分布在工作台 skill、内容库文件夹和独立插件中。用户决定把 beannote 作为内容生产平台建设；采集器和其他工具可以按技术选型并行存在，靠目录约定与素材格式协作，不要求统一语言、仓库或进程。

## 需求理解

搭建清楚、可扩展的 beannote 内容生产平台目录与协作边界：主题是内容生产工作单元；共享规则和知识进入平台知识库；采集、排版、发布等工具各自独立，通过可追溯的输入输出连接。现有 Chrome 插件保留，本地 Python 采集器作为并行工具落在平台 `tools/`。

- 工作台是另一个 Go 工具/仓库，和 beannote 并行。工作台继续承载 skills、任务、开发记录；beannote 承载内容与其专属工具。跨仓通过明确路径、素材格式和开发任务衔接。

## 内容流转

```text
B站链接 / 浏览器当前页面
       ↓
Chrome 插件（快速）或 Python 本地采集器（批量）
       ↓
来源包：source.json + 原字幕/机器转写 + SRT/TXT
       ↓ 用户选择归属
主题目录的 source/ → 内容核查与观点讨论 → 发布稿 → 排版/发布工具 → 发布记录
       ↘ 已核实且跨主题复用的知识 → kb/
```

平台字幕、平台 AI 字幕、机器转写和人工修订必须保留不同来源记录。资料包记录原 URL、平台 ID（含分 P）、标题、作者、采集时间、字幕语言/类型、处理引擎/模型和状态；不得将弹幕混作字幕，也不将 ASR 标成作者原文。

## 验收标准

- 目录说明能明确指出内容主题、跨主题知识、共享内容规范、工具代码、运行数据分别放在哪里。

## 风险与回滚

- 若将采集结果直接铺进 Git，会造成媒体文件和模型缓存膨胀；运行数据必须隔离，只有长期引用的轻量来源材料进入主题仓。
- 过早做跨平台抽象会让目录和接口复杂化；首版以 B 站实际实现验证边界。
- 两个采集入口可能产生不同字段；先约定来源包 schema，再做导入适配。
- 回滚本地工具可停用 `tools/source-collector/` 并保留插件。主题已有资料仍是普通文件，不依赖数据库才能阅读。
