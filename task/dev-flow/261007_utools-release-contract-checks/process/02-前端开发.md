## 得到的结论

- 共享协议是 API path、Req/Resp 与协议枚举唯一来源；缺契约时必须先核验后端并补协议仓，客户端不得保留手写路径兜底。
- 状态筛选代码原本有保存动作，问题主要是默认走浏览器 localStorage，uTools 生命周期下恢复不稳定；迁移到原生 dbStorage 并保留旧值迁移：`src/utils/cache-manager.ts`、`src/stores/plan.ts`。
- 全仓 ESLint 当前有 48,182 项存量问题，CI 只 lint 新增契约检查脚本并在 README/AGENTS 中披露范围：`package.json`、`README.md`。
- 业务层现存 Repo/Store 是当前 uTools 业务逻辑结构，不是新接口接入的强制架构；新增调用直接消费 contract API，并把必要的业务编排留在 composable。
- 迁移后 store/composable 直接调用 `src/contract.ts` 绑定的契约 API；字段映射只保留 UI 必需的 `RecentTask.completed` 派生值，任务和主题日志旧 Repo 中重复字段拷贝、API 请求日志包装不再存在。
- 后端已实现记录及所有后代记录的级联删除：`business-repo/backend-superone/internal/repo/topic_repo.go`。
