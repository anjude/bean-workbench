# MVP 技术选型与运行架构

> 历史讨论资料：Cocos 选型仍供参考；用户后来决定首个 MVP 在本地运行对战与脚本对手，本文的后台对局建议已不适用。当前方案见 [本地对战 MVP 方案](../../plans/本地对战MVP方案.md)。

## 结论

**建议沿用 Cocos Creator 3.8.8 作为小游戏客户端，并由 `backend-superone` 的 Go 服务运行权威对局和脚本对手。** 现有 `crazy-goose` 工程已使用该版本，Cocos 官方文档列出微信小游戏和抖音小游戏为支持的发布目标。当前玩法以 2D 赛道、卡牌交互、单位动画及割草怪物为主，没有需要换引擎的性能或能力理由。

这个结论针对可玩的 MVP 技术路线。割草副本实际怪物数量、粒子数量、最低设备表现以及小游戏主包体积，仍需在后续真实目标端构建和试玩中验证；不能只凭引擎选型推断最终性能。

## 用户本轮提出的 MVP 范围

- 先做核心玩法 MVP，不在本轮开始实现。
- 对局对手由后台逻辑控制，按项目定义的固定策略出牌与选择赛道。
- 因用户提出后台脚本对手，本文暂按“玩家对系统策略对手”估算；真人匹配及邀请好友对战不进入第一版核心玩法验证，之后可在同一对局规则上扩展。若这并非用户本意，需要在完整方案中修正范围。

## 技术依据

- 客户端仓 `business-repo/crazy-goose` 已是 Cocos Creator 3.8.8 微信小游戏项目，当前 `release` 分支工作区干净；工程已有运行时 TypeScript UI 和微信小游戏构建配置。
- Cocos Creator 3.8 官方跨平台发布文档列出微信小游戏、抖音小游戏；抖音开发者文档确认 Cocos 已完成适配，可由引擎直接导出小游戏产物。[Cocos 跨平台发布](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/) [抖音平台引擎适配说明](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide/game-engine/cocos-laya-egret)
- `business-repo/backend-superone` 使用 Go + Gin，已有 `/api/so/realtime-room/ws` WebSocket 接入、JWT 身份校验、Redis 房间状态和跨实例事件广播；这是传输及临时状态的基础，不是已经实现的游戏服务器。
- 现有 `internal/domain/realtime_room` 接受通用房间数据、做版本比较和 Redis 发布订阅，不包含战斗时钟、单位规则、AI 策略或胜负结算。因此不应把可信战斗状态塞进客户端可自由设定的通用 `data`，也不应把这层误当作完整战斗引擎。

## 建议的职责划分

| 部分                     | 职责                                        | MVP 处理                                          |
| ---------------------- | ----------------------------------------- | ----------------------------------------------- |
| Cocos Creator 客户端      | 场景、卡牌和赛道表现、拖放输入、动效音效、插值表现服务端状态、断线提示       | 保持 3.8.8；新增游戏场景与 TS 组件；输入只发送“部署哪张牌到哪条线”等玩家指令    |
| `backend-superone` 游戏域 | 创建对局、校验玩家操作、运行对局规则、执行脚本对手策略、决定胜负与奖励       | 新增专属 game/battle 域；策略在服务端执行，客户端不能决定对手行为、真实战力和结果 |
| WebSocket 层            | 低延迟承载玩家指令、服务端事件和对局状态快照                    | 优先评估复用当前 WSS 鉴权与连接骨架；游戏消息/协议和房间状态由专属域定义         |
| Redis                  | 暂存进行中的对局状态、时钟检查点和过期清理；承接多实例共享状态（如部署确实多实例） | 只存短期比赛状态并设 TTL；具体字段、原子操作和恢复规则在完整设计中确定           |
| MySQL                  | 持久化玩家卡牌、养成资源、结算奖励及必要战绩                    | 不按渲染帧或每个战斗 tick 写库；最终结算由服务端幂等落账                 |
| 微信/抖音平台适配              | 登录凭证、分享、广告、构建配置与生命周期差异                    | 先用当前微信小游戏验证 MVP；平台调用收口到客户端适配模块，避免规则代码直接依赖单端 API |

## 对局运行建议

1. **后台掌握正式状态。** 服务端保存双方手牌、单位、各赛道状态、基地血量、随机序列、对局阶段和结果。客户端只提交合法操作，收到服务端确认与状态变化后播放相应动画。
2. **固定规则驱动的策略对手。** 后台策略读取当前战场、对手压力、可用手牌及冷却状态，再按明确优先级选择卡牌和赛道。策略规则固定、可复现；每步决策根据局势变化，而不是预录一条必胜脚本。
3. **按事件和有限频率同步。** 手牌部署、刷新、赛道突破和胜负等关键变化实时推送；移动/对冲展示按较低频率发送状态或事件，由客户端补间动画。不要让客户端每帧向后端请求，也不要用高频短轮询模拟实时对战。
4. **临时状态与长期资产分开。** 对局期间状态使用有过期时间的在线存储；获胜奖励、卡牌经验等只在服务端确认结算后写入持久化数据。超时、重复提交、重连和对局结束后的重放由游戏域明确处理。
5. **先跑通单服短局。** MVP 可先在现有 Go 服务和 Redis 基础上实现短对局，验证单位部署、赛道压力、脚本对手、胜负反馈和结算；若运行部署存在多实例，再将对局所有权、Redis 原子更新及断线恢复纳入正式设计，不先引入新的专用游戏服务器技术栈。

## 选型风险与下一阶段设计点

- **MVP 的对战入口。** 旧玩法描述包含匹配对战和邀请好友；后台脚本对手适合先验证主玩法，但这会把 MVP 收敛为玩家对系统对手。第一版 UI 不应暗示正在和真人对战。真人匹配与好友房可后续加在相同的服务端规则上。
- **对战节奏和推送负载。** 需要先定短局长度、赛道数量、出牌刷新频率和单位数量，再确定快照频率和重连状态。对这种数值策略局，不需要帧同步；服务端按逻辑 tick/事件处理即可。
- **定时器和实例归属。** 需要检查实际部署进程数与负载均衡方式。内存中的 ticker 仅适合单实例临时原型；正式状态需能在 Redis/数据库恢复，或由固定对局 worker 持有，不能假设请求会持续落到同一进程。
- **脚本对手的难度与可解释性。** 对手应有清楚的强度档位和失误/反应节奏，避免每局总能瞬时针对玩家；保存策略版本和回放所需输入，便于调整胜率与复盘。
- **割草模式性能。** Cocos 能渲染 2D 割草玩法，但实际风险来自同屏怪物、投射物、碰撞与特效数量以及手机性能差异。其纳入 MVP 时要用目标设备压测；否则先用低实体数量的占位版本验证主对战。
- **跨平台不是零成本。** Cocos 支持两平台构建，但平台登录、网络域名白名单、WebSocket 行为、广告、分享、资源包体和审核需分别适配。抖音网络 API 要配置备案 HTTPS/WSS 域名白名单；正式跨平台验收不能只看一次 Cocos 构建成功。[抖音小游戏网络请求说明](https://partner.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide)

## 当前判断

- Cocos Creator 3.8.8：**适合继续用于客户端 MVP**。
- `backend-superone` Go：**适合承载服务端游戏规则和脚本对手；需新增专属游戏域，不能只复用通用房间快照接口**。
- WSS：**适合承载实时指令与状态推送**；Cocos 官方将 WebSocket 作为游戏实时服务端交互方式，抖音小游戏提供 `tt.connectSocket` 并要求 WSS 与合法域名。[Cocos WebSocket 概述](https://docs.cocos.com/creator/3.8/manual/en/advanced-topics/websocket-introduction.html) [抖音 `tt.connectSocket`](https://partner.open-douyin.com/docs/resource/zh-CN/mini-game/develop/api/javascript-api/network/websocket/tt-connect-socket)
- 真人匹配、好友邀请、赛季/排名、完整割草关卡和双平台广告：**不作为当前对战 MVP 技术验证的前置条件**；如要纳入首发完整产品，再单独设计。

## 代码与任务影响

本轮只是技术选型评估，没有改动业务仓代码、接口、契约、数据库或平台配置。完整功能方案仍需进一步明确：战斗规则与数据结构、对局连接及快照消息、策略对手规则、客户端状态矩阵、断线与重连、结算与验证场景。方案确认后再实施。
