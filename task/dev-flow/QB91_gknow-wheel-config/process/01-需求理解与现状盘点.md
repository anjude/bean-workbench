## 得到的结论

- **探索入口不是全量后端配置。** 分类标题/说明、入口卡片、分组顺序、路径、图标和部分文案保存在 `src/data/projectCatalog.ts`；首页通过 `useHomeCatalog` 直接从静态数据构建分类，见 `business-repo/uni-gknow/src/data/projectCatalog.ts`、`business-repo/uni-gknow/src/composables/useHomeCatalog.ts`。
- **性格盲盒中的测试条目和题目内容由后端提供。** `personality-box` 页面读取 assessment list 并呈现远端 title、summary、logo；测试详情由配置化答题页读取。页面标题、介绍、分类筛选标签及筛选映射仍写在前端，见 `business-repo/uni-gknow/src/pages/quiz/personality-box/index.vue`、`business-repo/uni-gknow/src/pages/quiz/configured/index.vue`。
- **人生、恋爱、理财副本的副本条目与剧本正文由后端提供。** 三个目录通过 `useStoryCatalog` 按 story type 获取列表，播放页获取 `contentJson`；目录页标题、简介和页面类型仍是小程序内固定实现，见 `business-repo/uni-gknow/src/composables/useStoryCatalog.ts`、`business-repo/uni-gknow/src/pages/game/life-copy/index.vue`、`business-repo/uni-gknow/src/pages/game/love-copy/index.vue`、`business-repo/uni-gknow/src/pages/game/finance-copy/index.vue`。
- **后端目前有 assessment 与 story 的内容 CRUD/查询接口，没有探索页目录或页面编排接口。** 路由见 `business-repo/backend-superone/app/api_service/api_gknow.go`；故事服务负责列表、详情、创建、更新，见 `business-repo/backend-superone/internal/domain/story/story_service/story_service.go`。
- 因此，以“从探索页调整分类、入口、分组或页面文案都不改版”为验收标准，当前**没有全量后端配置化**；目前完成的是测试和副本内容配置化，不包括小程序导航与页面壳层。

## 2026-11-09 第 3 轮 · 用户副本与多级筛选

### 用户明确的规则

1. 系统转盘及系统选项仅由 admin 维护，普通用户只读。
2. 用户新增或修改系统选项时创建本地用户副本；此后任何用户改动都不影响系统转盘。
3. 用户可创建本地自定义转盘和选项。
4. 从系统转盘创建的本地副本可按原 `wheel_key` 同步系统最新选项；同步前必须提示用户，用户可取消。系统来源的同项以系统版本覆盖；纯用户新增项和没有系统冲突的用户项保留。

### 现状与设计建议

- 当前一级分类与二级地区是两个独立筛选维度，不是父子级联；都只过滤候选列表，已勾选项仍参与转盘。分类、地区字段与筛选 UI 写死在小程序代码中。
- 建议将筛选表达为多个独立 filter group，每组用 `node_id` / `parent_id` 表示任意深度树。地区组可从国家扩到省、市、区；分类组也可按需分层。系统副本同步时需同步系统筛选树，用户自定义转盘使用同一结构。
- 用户副本保留 `source_wheel_key`、`source_version`；系统来源选项保留稳定 `source_option_id`，匹配 ID 而非名称，防止同名用户自定义项被误覆盖。
- 待进一步定规则：系统删除的选项在副本同步时如何处理；新增系统选项是否默认勾选；用户新增/修改内容创建副本，但筛选和勾选等个人偏好是否只保存在独立偏好中（建议不触发副本）。


## 2026-11-09 第 4 轮 · 操作日志与维度标签模型

### 已对齐并覆盖第 3 轮方案建议

- 系统转盘普通用户只读；本地选项新增、修改、删除作为按 `wheel_key` 归属的有序操作日志。每次读取最新系统配置后直接重放，不保存系统快照、不单独给日志加版本、不提供系统同步按钮。
- 只有用户明确点击“复制为我的转盘”时才物化独立自定义转盘；复制内容为系统配置加本地日志重放后的有效结果，复制后与系统盘隔离。也支持从空白创建本地转盘。
- 操作日志以稳定 `option_id` 定位；系统同 ID 更新由本地操作覆盖。
- 选项 tags 按筛选维度分组。后端按维度聚合标签返回前端；同行 OR、跨行 AND、未选维度不限制。筛选维度之间无级联关系，不接入 `address_tab`。
- 当前前端只有新增自定义项和勾选状态，没有选项内容编辑/删除交互；编辑/删除日志属于本次新增能力。
# 2026-11-10 多人转盘与抽签补充

- 用户确认多人实时转盘由房主转动，房间上限 100 人；新增抽签玩法，参与者进入房间即成为候选。
- 用户确认房主本人参加抽签，抽中后默认保留，允许手动移出。多人共同提交选项仍属于另一种玩法，最终转盘和历史由各设备保存。
- 现有实时房间服务限制 8 人、2 小时和 32 KB 共享数据，且每次事件需每连接读取房间；100 人需要扩容设计与验证，不能仅修改上限。详见 [多人转盘与抽签玩法草案](../plans/多人转盘与抽签玩法.md)。


## 多人房间通用化

- 用户希望后端只提供通用房间能力，后续接入玩法时无需增加房间业务逻辑。当前未部署的专用多人转盘实现把抽签、轮次和结算写进服务端，需要重新划分边界。
- 建议在现有实时房间上补齐通用集合、权限和版本控制。后端管理成员、房主身份、记录归属、版本比较、原子提交、请求去重、过期和变更通知，房间数据的业务含义由客户端定义。现有默契房间调用方式应继续兼容。
- 转盘客户端负责从成员生成候选、冻结名单、抽签、停止、记录历史及本机保存。房主提交共享结果时，后端仅校验通用房主写权限和期望版本。其他设备读取同一已提交结果，断线后按版本补齐。
- Redis Hash 可作为分记录存储。内容哈希可用于核对同一份冻结快照，版本比较与原子提交负责并发一致性。两者均不能证明房主客户端按公平规则抽签。旧方案中“服务端选出结果”与新边界的取舍待确认。
