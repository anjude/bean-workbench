## 设计结论

- 系统转盘列表和每个转盘的选项由后端托管；Agent 通过 Gknow admin API 创建、编辑、排序、发布和下架，沿用盲盒测试与人生副本的管理模式，不建设管理后台。
- 后端系统数据使用两张表：wheel 主表保存元数据、文案、筛选维度和配置版本；option 子项表每条候选项一行，保存稳定 ID、名称、tags 和排序。
- “去哪玩”的系统 `wheel_key` 使用 `where-to-go`，不绑定城市或国家；前端只消费 API 返回的 wheel key，不保留 key 白名单或旧 `theme` 映射。首批配置可全部从后端删除，列表为空时前端展示空态；数据模型允许后续新增全国及其他国家地区的配置。
- 业务泳道图采用连续表格：管理员/Agent、后端、小程序、使用者各为一列，列间紧邻共边界；配置维护、用户使用为阶段行，跨列箭头表示角色交接。
- 普通用户只读系统转盘；新增、修改、删除选项按 `wheel_key` 追加本地操作日志，读取系统数据后依序重放。只有用户明确复制或从零新建时，才保存无来源关联的独立自定义转盘。
- 不为本地日志另存系统快照或维护日志版本。系统 `content_version` 用于后端配置并发控制；小程序可用它作为运行期计算缓存键。
- 选项 `tags` 按筛选维度 key 分组；后端按维度聚合、去重并返回标签行。同行 OR、跨行 AND，未选择的行不参与过滤。
- 分类、地区、场景均作为普通标签维度，不做级联，不接入地址表；维度 key 保证同名标签不会串行。
- 新分享链接使用动态 `wheel_key`；旧 `theme=...` 链接不兼容。客户端只走远程配置，不保留静态题目兜底。
- 当前本地静态数据共 202 项（食物 46、深圳去处 56、周末活动 100），可作为后台首批 seed 内容；升级时不迁移旧勾选或自定义项。系统 `option.id` 稳定且不复用，供本地操作日志定位系统选项；用户副本不再同步系统。
- 旧版 `customOptions`、勾选状态和筛选偏好不迁移；升级时清理旧存储，按新模型初始化。系统盘显式复制时复制有效选项、筛选维度及当前勾选结果，生成新的 `wheel_id` 后与系统盘隔离。
- 业务流程泳道图及系统时序图已按当前模型更新，方案包含接口、JSON、DDL 草案、迁移、错误处理和验收矩阵。

## 2026-11-10 补充对齐

- 系统配置表确定为两张：`gknow_wheel_tab` 存转盘信息、筛选维度和版本；`gknow_wheel_option_tab` 每个候选项一行，存稳定 option ID、名称、tags、排序和扩展信息。用户日志、自定义转盘仍只存在本机，不增加后端表。
- “去哪玩”由深圳专用 key 改为通用稳定 key `where-to-go`。不兼容 `theme=shenzhen`，也不迁移旧 wheel 本机数据；首批内容仍为深圳 56 项，但前端不依赖该初始清单。
- 为后续全国及其他国家地区扩展，去哪玩可配置 `country`、`region1`、`region2`、`city`、`district` 等普通 tag 维度；每个选项带有适用的层级标签。筛选维度仍彼此独立，前后端不接入地址表或级联逻辑。
- 详情 API 聚合两表返回配置、子项和按维度汇总的筛选值；admin 更新在事务内 upsert 子项、明确删除指定 ID，并递增 wheel 配置版本。
- admin 删除 wheel 时，后端按版本校验后事务删除 wheel 主记录及其全部子项；前端直接呈现远端列表变化，不设置本地隐藏或退役逻辑。删除过的 key 不复用。
